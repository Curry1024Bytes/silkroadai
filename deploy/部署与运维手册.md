## 0. 全新服务器从零部署 / 灾备重建

本节是新服务器、系统重装或灾备重建的主流程。当前新环境使用
`1226287131-ui/new-api-custom-full` 的源码和本仓库中的正式 Compose 模板；第 2、7、8.3 节中
带有 MySQL、`calciumion/new-api` 或手工 `docker run` 的内容是旧服务器审计记录，不能用于新环境。

先区分两种场景：**全新安装**使用空的 Docker volume，生成新的随机密钥，然后运行 0.3--0.11；
**灾备重建**必须保留原来的 `SESSION_SECRET`、`CRYPTO_SECRET`、数据库、`/opt/new-api/data`、`.env`、
证书和经过审阅的源码 SHA，先按 0.12 恢复到隔离环境并完成校验，再开放 DNS 和公网流量。灾备场景
不能重新生成这些密钥：`SESSION_SECRET` 会使现有会话/刷新凭据失效，`CRYPTO_SECRET` 会使 HMAC
缓存键和任务签名不一致；Portal 的 `PORTAL_OSS_ENC_KEY`、`ENTERPRISE_UPSTREAM_ENC_KEY` 更不能更换，
否则 Portal 已保存的加密凭据无法解密。也不能把全新安装步骤中的空库或 `migrate reset` 用在恢复数据上。

### 0.3 初始化 CentOS Stream 9 主机

以下命令在新服务器的 root shell 执行。发行版包名若有变化，以 `dnf` 的实际结果为准：

```bash
set -euo pipefail
timedatectl set-timezone Asia/Shanghai
dnf -y update
dnf -y install git curl ca-certificates openssl nginx firewalld fail2ban policycoreutils-python-utils dnf-plugins-core
# Configure Docker CE from its official CentOS repository, then install Engine and Compose.
dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
dnf -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker
systemctl enable --now firewalld nginx fail2ban
install -d -m 755 /etc/fail2ban/jail.d
cat >/etc/fail2ban/jail.d/sshd.local <<'EOF'
[sshd]
enabled = true
port = ssh
backend = systemd
maxretry = 5
findtime = 10m
bantime = 1h
bantime.increment = true
bantime.factor = 2
bantime.maxtime = 24h
EOF
systemctl restart fail2ban
fail2ban-client status sshd
setsebool -P httpd_can_network_connect 1
firewall-cmd --permanent --add-service=ssh
firewall-cmd --permanent --add-service=http
firewall-cmd --permanent --add-service=https
firewall-cmd --reload

docker version
docker compose version
docker info --format '{{.DockerRootDir}}'
getenforce
getsebool httpd_can_network_connect
```

保持 SELinux 为 enforcing。Compose 对 new-api 数据和日志 bind mount 使用 `:Z` 私有标签；Nginx 代理到
Portal 的本机上游需要 `httpd_can_network_connect`。SELinux 被禁用的现有主机无需执行 `setsebool`，但
全新安装不要为省事关闭 SELinux。

写入 SSH 公钥后，先开第二个 SSH 会话验证，再加固 SSH：

```bash
install -d -m 700 /root/.ssh
touch /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
cat >> /root/.ssh/authorized_keys <<'EOF'
<operator 的 SSH 公钥>
EOF
cat >/etc/ssh/sshd_config.d/00-llmroute-hardening.conf <<'EOF'
PermitRootLogin prohibit-password
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
MaxAuthTries 3
LoginGraceTime 30
EOF
sshd -t
systemctl reload sshd
sshd -T | grep -Ei 'permitrootlogin|pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication'
```

不要关闭当前已验证的 SSH 会话；先用新终端确认公钥登录成功，再结束旧会话。

### 0.5 部署 new-api-custom-full

先生成环境文件，权限必须为 `0600`：

```bash
cd /opt/new-api
cp /opt/silkroadai-portal/deploy/new-api-custom.env.example .env
for key in POSTGRES_PASSWORD REDIS_PASSWORD SESSION_SECRET CRYPTO_SECRET; do
  sed -i "s/^${key}=CHANGE_ME$/${key}=$(openssl rand -hex 32)/" .env
done
chmod 600 .env
install -d -m 700 data logs
```

检查 `.env` 中四个值均为不同的随机值。构建时不要直接把 `/opt/new-api` 作为 Docker build
context：目录内的 `.env` 虽被 Git 忽略，但上游 `.dockerignore` 没有排除它。用只含已记录 Git
提交内容的临时目录构建，避免把密钥、数据目录和本地文件送进 Docker build context：

```bash
set -euo pipefail
BUILD_DIR=$(mktemp -d /opt/new-api-build.XXXXXX)
trap 'rm -rf "$BUILD_DIR"' EXIT
git -C /opt/new-api archive --format=tar HEAD | tar -xf - -C "$BUILD_DIR"
docker build -f "$BUILD_DIR/Dockerfile.custom" -t new-api-custom:latest "$BUILD_DIR"
docker image inspect new-api-custom:latest --format '{{.Id}}'
docker compose --env-file /opt/new-api/.env \
  -f /opt/silkroadai-portal/deploy/new-api-custom-compose.yml config --quiet
docker compose --env-file /opt/new-api/.env \
  -f /opt/silkroadai-portal/deploy/new-api-custom-compose.yml up -d
```

首次启动可能需要等待数据库迁移。确认容器、端口、网络和状态接口：

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
docker compose --env-file /opt/new-api/.env \
  -f /opt/silkroadai-portal/deploy/new-api-custom-compose.yml ps
ss -lntp | grep ':3000'
curl --fail --max-time 10 http://172.17.0.1:3000/api/status
docker network inspect new-api_new-api-net >/dev/null
```

期望只有 `172.17.0.1:3000` 监听，`/api/status` 返回 JSON 且 `success:true`。若 Compose 变量为空，
先检查 `--env-file` 路径、`.env` 权限和四个变量，不要把真实值写进 Git。

### 0.7 安装 Nginx 和 Origin Certificate

```bash
umask 077
install -d -m 700 /opt/backups/nginx
tar -czf "/opt/backups/nginx/pre-install-$(date +%Y%m%d-%H%M%S).tgz" \
  /etc/nginx/nginx.conf /etc/nginx/conf.d 2>/dev/null || true
install -d -m 700 /etc/nginx/ssl
install -m 644 /secure-transfer/llmroute.club.pem /etc/nginx/ssl/llmroute.club.pem
install -m 600 /secure-transfer/llmroute.club.key /etc/nginx/ssl/llmroute.club.key
install -m 644 /opt/silkroadai-portal/deploy/nginx/llmroute-web.conf /etc/nginx/conf.d/llmroute-web.conf
install -m 644 /opt/silkroadai-portal/deploy/nginx/llmroute-api.conf /etc/nginx/conf.d/llmroute-api.conf
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -noout -subject -dates -fingerprint -sha256
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -pubkey -noout | openssl pkey -pubin -outform der | sha256sum
openssl pkey -in /etc/nginx/ssl/llmroute.club.key -pubout | openssl pkey -pubin -outform der | sha256sum
nginx -t
systemctl enable --now nginx
systemctl reload nginx
```

两条公钥哈希必须相同。配置中的 upstream 必须指向 `127.0.0.1:3002`；API virtual host 只放行
`/v1/*` 和 `/v1beta/*`，不能把公网 API 直接代理到 new-api。覆盖配置前先检查备份中的旧
`server_name`、ACME challenge location 和其他站点；Origin Certificate 模式不需要 ACME 自动续期，
但灾备恢复不能无意间删除仍在使用的 ACME 配置。

### 0.9 SSH 隧道访问 new-api 后台

Mac 的 `~/.ssh/config` 使用新服务器 IP，并确保别名的 ControlMaster 与转发一致：

```sshconfig
Host llmroute-prod
    HostName 103.240.199.146
    User root
    IdentityFile ~/.ssh/llmroute_ed25519
    IdentitiesOnly yes
    ControlMaster auto
    ControlPersist yes
    ControlPath ~/.ssh/llmroute-prod.sock
    Compression yes
    LocalForward 127.0.0.1:3000 172.17.0.1:3000
    LocalForward 127.0.0.1:3306 127.0.0.1:3306
    LocalForward 127.0.0.1:5432 127.0.0.1:5432
    ExitOnForwardFailure yes
    ServerAliveInterval 15
    ServerAliveCountMax 4
```

2026-10-13 已取消 Mac 长期后台隧道的 `ControlPersist 10m`，改为 `yes`，避免主连接空闲后
自动退出。排查时 XTerminal 到新服务器的 TCP 仍为 ESTABLISHED，但正式 master socket 不存在，
本机 3000 无监听；服务器 new-api healthy、源站 `/api/status` 为正常 200 JSON，默认算法仍为 BBR。
本机配置备份为 `~/.ssh/config.bak.llmroute-persist-20261013-112822`，只修改该别名的持久时限，
随后重建隧道。3000/3306/5432 均由新 master 监听，正式 3000 状态接口与首页 200，三个基础 JS
完整下载，内置浏览器已验证首页完整渲染。没有修改或重启服务器服务；3306 仍只是遗留监听，
不代表远端数据库可用。旧进程未保留退出日志，因此不把本次退出唯一归因于 10 分钟时限。
`ControlPersist yes` 不提供断网后自动重连，休眠或网络切换后的异常仍按下面步骤核验和恢复。

日常连接先验证已有状态接口，正常就复用；只有接口异常时才尝试补齐转发或新建 master：

```bash
if (curl --noproxy '*' --fail --silent --max-time 10 http://127.0.0.1:3000/api/status \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); sys.exit(0 if d.get("success") is True and isinstance(d.get("data"),dict) and "setup" in d["data"] else 1)') >/dev/null 2>&1; then
  ssh -O check llmroute-prod
elif ssh -O check llmroute-prod >/dev/null 2>&1; then
  ssh -O forward -o ExitOnForwardFailure=yes llmroute-prod
else
  ssh -fN -o ExitOnForwardFailure=yes llmroute-prod
fi
curl --noproxy '*' --fail --max-time 10 http://127.0.0.1:3000/api/status
```

`ssh -O check` 只代表 master 存在，不代表 3000 转发存在；`/api/status` 返回
`success:true` 只证明小请求可达，还必须下载当前首页引用的大 JS 并在浏览器中验证页面渲染。
对已存在的监听重复执行 `ssh -O forward` 会报端口占用；遇到部分转发缺失或其他进程占用时，先用
`lsof` 定位，只补缺失项，再验状态接口，不要盲目终止进程。3306 是迁移前遗留的运维转发，新服务器
远端 3306 没有服务；5432 对应 Portal PostgreSQL，已通过 PostgreSQL 协议探测确认隧道到达服务。
new-api PostgreSQL 没有发布宿主机端口，不能用这两项转发连接它。

换服务器、启用压缩或切换拥塞控制时，先保留旧连接，用一个独立 TCP 连接验证。先用
`lsof -nP -iTCP:3001 -sTCP:LISTEN` 确认测试端口空闲，再在 Mac 的单独终端前台运行：

```bash
ssh -F /dev/null -S none \
  -i ~/.ssh/llmroute_ed25519 \
  -o IdentitiesOnly=yes -o PreferredAuthentications=publickey \
  -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -o ControlMaster=no -o ControlPath=none -o Compression=yes \
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=4 \
  -N -L 127.0.0.1:3001:172.17.0.1:3000 root@103.240.199.146
```

`-F /dev/null` 避免继承别名中的其他转发，`-S none` 避免复用旧 master；不要加
`ClearAllForwardings=yes`，它会连显式 `-L` 一起清掉。严格主机校验要求已保存并核验新服务器的主机
指纹，不能用关闭校验来绕过错误。另一终端先请求
`curl --noproxy '*' --fail --max-time 10 http://127.0.0.1:3001/api/status`，再用 `curl --compressed`
完整下载首页实际引用的主 JS，核对 HTTP 200、压缩响应、下载完整性和耗时，最后打开
`http://127.0.0.1:3001/` 确认实际页面出现。静态文件名随构建变化，不能照抄历史文件名。

独立连接成功后再迁移正式端口。先记录旧 master 的实际 socket，选择一个尚未使用的新 socket；
本次由原 `~/.ssh/control-%C` 迁移到 `~/.ssh/llmroute-prod.sock`。先以新 socket 建立并认证正式
master，暂不加任何转发；只有确认新连接可执行远端命令后才交接监听，不能先关闭旧 master 再等待握手。
以下示例用于该新 socket 尚未被占用时：

```bash
ssh -F /dev/null -M -S ~/.ssh/llmroute-prod.sock \
  -i ~/.ssh/llmroute_ed25519 \
  -o IdentitiesOnly=yes -o PreferredAuthentications=publickey \
  -o BatchMode=yes -o StrictHostKeyChecking=yes -o Compression=yes \
  -o ControlPersist=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=4 \
  -fN root@103.240.199.146
ssh -F /dev/null -S ~/.ssh/llmroute-prod.sock root@103.240.199.146 true
```

两条命令都成功后，通过明确的旧 socket 执行 `-O cancel`，仅取消旧 master 的
3000/3306/5432 转发；保留其已认证连接和独立 3001 隧道。确认监听释放后，通过明确的新 socket
执行 `-O forward` 添加同样三个回环转发。操作时使用 `-F /dev/null` 与显式 `-L`，避免继承配置中的
重复转发。取消旧转发的 `-L` 监听地址必须与旧配置或创建命令一致；旧监听若省略 `127.0.0.1`，
cancel 也使用原省略形式。如添加失败，先恢复旧 master 的监听再排查。

随后备份并把 Mac 别名配置改为新 socket，验证正式 3000 的状态接口、大资源与浏览器页面，核对三个
监听由新 master 持有。全部通过后才用旧 socket 的 `-O exit` 关闭旧 master，并关闭测试 3001 隧道；
保留用户独立 shell。不删除 socket 文件来终止连接，也不以修改后的别名去猜旧 socket 路径。

压缩与默认拥塞算法都不会自动改变已经建立的连接。BBR 必须在服务器用实际 TCP 源端口关联
`ss -tinp` 验证；仅查看全局 `sysctl` 不能证明当前隧道已切换。JS 已 gzip 时，SSH 压缩通常收益有限。
本次新服务器的取证与验证边界见 [2026-10-12 SSH 修复报告](../docs/SSH-TUNNEL-REPAIR-2026-10-12.md)。

new-api 管理后台只通过这条 SSH 隧道访问，Compose 中因此使用
`SESSION_COOKIE_SECURE=false`，并且不设置 `SESSION_COOKIE_TRUSTED_URL`；否则浏览器在
`http://127.0.0.1:3000/` 下不会发送登录 Cookie，且 new-api 会拒绝不匹配的配置。

## 1. 分支与发布规则

三个长期分支的职责固定如下:

| 分支   | 职责       | 允许的操作                                           |
| ------ | ---------- | ---------------------------------------------------- |
| `main` | 上游镜像   | 只同步上游,不做项目自定义修改,不解决项目冲突,不部署  |
| `dev`  | 开发与集成 | 自研开发、合并 `main`、解决冲突、类型检查和完整测试  |
| `prod` | 生产发布   | 只接收测试通过的 `dev` fast-forward,VPS 只部署此分支 |

每次同步上游必须先报告、后执行。报告包括每个提交的北京时间、SHA、行为变化、migration、
环境变量、服务器/Nginx/Cloudflare/安全影响,以及与 `dev` 的差异和冲突预判。固定流程是:

```text
upstream -> main -> 变更报告 -> dev 合并/解决冲突 -> 完整验证
         -> prod fast-forward -> operator 明确安排 -> VPS 手动部署
```

CI 只做检查,不会自动部署。禁止从 `main` 直接上线。

2026-09-15 operator 已授权「做好并测试通过后直接上线」。对已安排的工作，该持续授权满足流程中的发布许可：检查通过后由 Codex 按本手册直接执行备份、迁移和部署，无须再次确认。后续明确的暂停或先沟通指令优先；实际改价、收费调用及未安排的改动不在此授权内。

### 2.2 当前容器和网络

| 容器                   | 当前用途             | 宿主机绑定        | 启动方式                                            |
| ---------------------- | -------------------- | ----------------- | --------------------------------------------------- |
| `silkroadai-portal`    | Next.js Portal       | `127.0.0.1:3002`  | `docker-compose.prod.yml` 的 `portal` 服务          |
| `silkroadai-portal-db` | Portal PostgreSQL 16 | `127.0.0.1:5432`  | `docker-compose.prod.yml` 的 `portal-postgres` 服务 |
| `new-api`              | 模型路由与计费       | `172.17.0.1:3000` | 手工 `docker run`                                   |
| `new-api-mysql`        | new-api MySQL 8      | 不发布宿主机端口  | new-api 原有 Docker 网络                            |

关键网络事实:

- new-api 和 MySQL 所在网络:`new-api_new-api-net`。
- Portal 的 compose 也会加入这个 external network,部署前该网络必须存在。
- Portal 仍通过 `NEWAPI_BASE_URL=http://host.docker.internal:3000` 访问 new-api。
- new-api 必须绑定 `172.17.0.1:3000`,不能绑 `127.0.0.1:3000`,否则 Portal 容器访问会被拒绝。
- 不要把 new-api 改成 `0.0.0.0:3000`,否则会扩大公网暴露面。
- new-api 持久化目录:`/opt/new-api/data -> /data`。
- 服务器上可能保留停止状态的 `new-api-old-port` 回退容器。确认新容器和备份稳定前不要误删。

`docker-compose.prod.yml` 还包含上游的 `portal-api-1..3` 和 `seedance-portal`,但已经用 Compose
profiles 隔离:

- `portal-api-1..3` 属于 `api-replicas` profile。
- `seedance-portal` 属于 `seedance` profile。
- 默认不启用 profile 时,只会启动主站 Portal 及其 PostgreSQL 依赖。

这台服务器当前只部署主站 Portal,日常发布仍显式指定 `portal`,让操作目标一眼可见:

```bash
docker compose -f docker-compose.prod.yml up -d portal
```

发布验收通过后执行一次保留策略清理。它只保留当前运行镜像、发布前创建的一个回滚镜像、最新一份
Portal PostgreSQL 备份和最新一份 `.env` 备份，不删除 Docker volume 或运行中的容器:

```bash
bash scripts/prune-production-retention.sh "$DEPLOY_ROLLBACK_TAG"
df -h /
```

如果清理脚本失败，保留现状并人工核对 `docker inspect silkroadai-portal`、回滚标签和两类备份，
不要用 `docker system prune` 代替；该命令可能删除未被容器引用的恢复材料。

如未来明确部署上游可选服务,必须显式启用对应 profile,例如
`docker compose -f docker-compose.prod.yml --profile api-replicas up -d`。不要在当前 LLmRoute
服务器启用未配置、未验收的 profile。

### 3.3 构建时变量

所有 `NEXT_PUBLIC_*` 都可能被 Next.js 编译进客户端产物。修改后必须重新 build,仅重启容器不可靠。
`docker-compose.prod.yml` 会从同目录 `.env` 读取以下公开变量,并作为 build args 传给 Dockerfile:

```env
APP_URL="https://llmroute.club"
NEXT_PUBLIC_APP_URL="https://llmroute.club"
NEXT_PUBLIC_API_URL="https://api.llmroute.club"
NEXT_PUBLIC_IMAGE_URL="https://images.llmroute.club"
NEXT_PUBLIC_SUPPORT_EMAIL="support@llmroute.club"
NEXT_PUBLIC_SUPPORT_WECHAT="LLmRoute"
```

Dockerfile 对这些变量也提供 LLmRoute 默认值,避免直接构建时回落到上游旧域名。标准生产构建不再需要逐个手写
`--build-arg`;先核对 `.env`,再执行:

```bash
docker compose -f docker-compose.prod.yml build portal
docker compose -f docker-compose.prod.yml up -d portal
```

纯运行时变量修改后可执行 `up -d portal`;只要改了代码或 `NEXT_PUBLIC_*`,就按上面的 build + up 两步执行。

### 3.4 不可轮换项

- `PORTAL_OSS_ENC_KEY` 用于解密客户已保存的 OSS Secret。投产后不能随意更换,否则历史配置无法解密。
- new-api 后台“系统访问令牌”的生成操作是 rotate。重新生成会立即让旧 `NEWAPI_ADMIN_TOKEN` 失效。
- 数据库密码修改需要同时处理 `.env`、PostgreSQL 用户和现有 volume,不能只改模板。

### 4.4 拉取并部署

生产构建统一使用本节的 Git 归档上下文；本手册其他位置的 `build portal` 示例也须采用该方式，避免把服务器配置备份复制进镜像构建层。

```bash
cd /opt/silkroadai-portal
git switch prod

# 备份所需的 077 不得带入源码拉取。先恢复标准权限掩码并记录回滚点。
umask 022
test "$(umask)" = "0022"
DEPLOY_PREV_SHA=$(git rev-parse HEAD)

git pull --ff-only origin prod
git log -1 --oneline

# Prisma runner 是非 root 用户。修复并检查所有 schema/migration 对容器用户可读。
chmod -R a+rX prisma
test -z "$(find prisma -type d ! -perm -0555 -print -quit)"
test -z "$(find prisma -type f ! -perm -0444 -print -quit)"
git diff --name-status "$DEPLOY_PREV_SHA"..HEAD -- prisma/migrations prisma/schema.prisma

# 必须在 build 之前给线上旧镜像打回滚标签。VPS 用 containerd 镜像存储，旧镜像若只有
# latest 一个名字，build 把 latest 指向新镜像后旧镜像即不可寻址，事后 tag / commit 都会失败。
# 任一命令失败就停止发布，不要继续 build。
DEPLOY_TS=$(date -u +%Y%m%d-%H%M%S)
DEPLOY_ROLLBACK_TAG="silkroadai-portal-portal:rollback-$DEPLOY_TS"
DEPLOY_OLD_IMAGE=$(docker inspect -f '{{.Image}}' silkroadai-portal)
docker tag "$DEPLOY_OLD_IMAGE" "$DEPLOY_ROLLBACK_TAG"
test "$(docker image inspect -f '{{.Id}}' "$DEPLOY_ROLLBACK_TAG")" = "$DEPLOY_OLD_IMAGE"
echo "rollback: $DEPLOY_ROLLBACK_TAG -> $DEPLOY_OLD_IMAGE (git $DEPLOY_PREV_SHA)"

# 服务器的 .env.bak.* 等备份不能进入构建上下文；仅归档当前 prod 提交的源码。
# 公开 build args 仍由原生产 Compose 和同目录 .env 提供。
DEPLOY_CONTEXT_DIR=$(mktemp -d /tmp/llmroute-build.XXXXXX)
mkdir "$DEPLOY_CONTEXT_DIR/source"
git archive HEAD | tar -x --exclude=.env --exclude='.env.*' -C "$DEPLOY_CONTEXT_DIR/source"
chmod -R a+rX "$DEPLOY_CONTEXT_DIR/source/prisma"
python3 - "$DEPLOY_CONTEXT_DIR" <<'PY'
import json, pathlib, sys
p = pathlib.Path(sys.argv[1])
(p / 'context.json').write_text(json.dumps({
    'services': {'portal': {'build': {'context': str(p / 'source')}}}
}))
PY
docker compose -p silkroadai-portal -f docker-compose.prod.yml \
  -f "$DEPLOY_CONTEXT_DIR/context.json" build portal
# 新镜像同时打 release 标签，作为下一次发布的回滚点。
docker tag silkroadai-portal-portal:latest "silkroadai-portal-portal:release-$(git rev-parse --short HEAD)"

# 只启动一次性检查容器,不执行 start.sh、不连接数据库、不切换线上容器。
# 禁用交互 stdin，避免通过 ssh bash -s 发布时吞掉后续脚本。
docker compose -f docker-compose.prod.yml run --rm --no-deps -T --interactive=false --entrypoint sh portal -c \
  'test -r prisma/schema.prisma && find prisma/migrations -type f -name migration.sql -exec test -r {} \;'

docker compose -f docker-compose.prod.yml up -d portal
```

`start.sh` 会在容器启动时自动执行 `prisma migrate deploy`,然后启动 Next.js。不要手工修改 migration 历史,
也不要在生产库执行 `prisma migrate reset`。`chmod -R a+rX prisma` 只增加读取/目录遍历权限,不会修改 SQL
内容;Dockerfile 还会把 runner 中的 Prisma 文件交给 `nextjs:nodejs` 并再次保证可读。

若权限检查或一次性容器检查失败,不要执行 `up -d portal`,线上旧容器继续运行。先检查本次新增文件的
属主和 mode:

```bash
find prisma/migrations -maxdepth 2 -printf '%M %u:%g %p\n' | tail -30
docker compose -f docker-compose.prod.yml run --rm --no-deps -T --interactive=false --entrypoint sh portal -c \
  'id; find prisma/migrations -maxdepth 2 -exec ls -ld {} \; | tail -30'
```

若启动时报 Prisma `P3015` / `migration.sql missing`,先按上述命令确认“宿主机文件存在但 runner
不可读”。在确认数据库 `_prisma_migrations` 状态前,禁止运行 `prisma migrate resolve`、禁止补造空 SQL、
禁止删除 migration 目录、禁止恢复数据库。权限修好后重新 build 并再次运行只读检查;只有检查通过才切换
容器。若文件在 Git 中确实不存在,停止发布并回到本地修复提交历史,不要直接在 VPS 手工补文件。

构建阶段若出现 `Can't resolve '@vercel/turbopack-next/internal/font/google/font'` 或 `next/font/google
queries have exactly one entry`,是构建时拉取 Google Fonts 的网络瞬断,与代码无关;线上旧容器不受影响,
确认 `curl -I https://fonts.googleapis.com` 可达后直接重跑同一条 build 命令即可(2026-09-24 实测重跑成功)。

## 6. Nginx 与 Cloudflare

### 6.1 当前证书

```text
/etc/nginx/ssl/llmroute.club.pem
/etc/nginx/ssl/llmroute.club.key
```

私钥权限必须是 600。证书为 Cloudflare Origin CA,有效期核验:

```bash
chmod 600 /etc/nginx/ssl/llmroute.club.key
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -noout -subject -issuer -dates -ext subjectAltName
```

证书和私钥匹配核验:

```bash
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -pubkey -noout \
  | openssl pkey -pubin -outform der | sha256sum
openssl pkey -in /etc/nginx/ssl/llmroute.club.key -pubout \
  | openssl pkey -pubin -outform der | sha256sum
```

两个 SHA-256 必须完全相同。

### 6.2 当前主站路由要求

Nginx 中 `llmroute.club` 和 `www.llmroute.club` 应共同反代 `127.0.0.1:3002`,HTTP 跳 HTTPS。
仓库基线模板为 `deploy/nginx/llmroute-web.conf`,生产安装路径为
`/etc/nginx/conf.d/llmroute.club.conf`。不要只在服务器临时 `sed`,否则配置无法审计和复现。
该模板的 access log 只记录 `$uri`,不记录 query string,避免 OAuth code、密码重置/邮箱验证 token 和
支付回调签名落盘。
`/image-adapter/*` 是 new-api 的内部上游适配器,主站 Nginx 必须对公网返回 404。若未来启用该图片渠道,
new-api 的 Base URL 使用共享 Docker 网络地址
`http://silkroadai-portal:3002/image-adapter/ominiapi`,上游 Key 只保存在 new-api 渠道配置中;禁止改成
`https://llmroute.club/image-adapter/ominiapi` 绕公网调用。
修改任何 Nginx 配置后统一执行:

```bash
nginx -t && systemctl reload nginx
```

Cloudflare DNS 的 apex 与 `www` 记录都应指向 `103.240.199.146` 并开启橙云。SSL/TLS 模式保持
**Full (strict)**,不要使用 Flexible。

### 6.3 `api.llmroute.club` 独立入口

- 只有 `/v1/*`、`/v1beta/*`,以及火山方舟原生视频的提交 `/api/v3/contents/generations/tasks` 和单任务查询
  `/api/v3/contents/generations/tasks/{id}`(2026-10-29 起)对公网开放,都先进入 Portal `127.0.0.1:3002`;

```bash

# 确认上面的命令没有监听输出后，再执行：

ssh -O check llmroute-newapi
```

日常使用前面的分支命令：master 已存在时补齐配置里的端口转发，不存在时新建连接；
转发失败直接显示错误，不将端口占用等错误误当成“没有master”再尝试新建。
仍须以 `/api/status` 的 HTTP 200 和 `success:true` 确认 new-api 实际可达。
`ssh -O check` 只检查 master 进程，不能证明 3000 正在监听或远端服务可达。
2026-09-14 实测 master 存在但没有任何本地监听，旧 check-or-connect 因此跳过建立隧道；
`ssh -O forward llmroute-newapi` 在同一 master 上补齐转发后恢复，再次执行也成功，未中断已有连接。

运维命令若使用 `ClearAllForwardings=yes`，须同时设置 `ControlPath=none` 与 `ControlMaster=no`，
使用独立连接，避免在隧道的 control socket 上留下没有转发的后台 master。
本次修复未改 Mac SSH 配置或重启线上服务。`exit` 会关闭该 master 及其复用会话。
不要通过删除 control socket 来重连：删 socket 不会关闭旧 SSH 进程。
`ssh -O check` 失败也不能单独证明进程不存在；还须核对 `lsof` 的监听 PID 和进程命令，
确认无旧 master 且 socket 确实陈旧后，才将旧 socket 改名留档。

未配置该别名或本地 3000 端口冲突时,可使用独立的 18082 端口:

```bash

  -i "$HOME/.ssh/llmroute_ed25519" \
  -o IdentitiesOnly=yes \
  -o IPQoS=none \
  -o TCPKeepAlive=yes \
  -o ServerAliveInterval=15 \
  -o ServerAliveCountMax=4 \
  -o ExitOnForwardFailure=yes \
  -o ControlMaster=no \
  -o ControlPath=none \
  -L 127.0.0.1:18082:172.17.0.1:3000 \
  root@82.29.71.122

curl --max-time 10 http://127.0.0.1:18082/api/setup
```

返回 `success:true` 后浏览器打开 `http://127.0.0.1:18082/`。`-f` 会让隧道在认证完成后进入后台;
查看时先核对监听 PID 和完整进程命令：

```bash

```

再用 `ps -p <PID> -o pid,ppid,command` 确认它就是刚建立的 SSH 隧道，才用 `kill <PID>` 停止。
不要按端口直接批量 kill，也不要用宽泛 `pkill`。`-F /dev/null` 排除别名附带的转发，
`ControlPath=none` 避免复用已有 master；仅 `ControlMaster=no` 不保证独立连接。

3. 维护期间禁止另一个管理员编辑 new-api 价目或渠道。API 没有跨 option/channel 事务和 CAS。
4. 保留当前 `prod` SHA、Portal 镜像 ID、new-api 镜像 digest 和脚本快照路径。

维护开始后在 VPS 先停 Portal,再停止共用 MySQL 和 `/opt/new-api/data` 的旧容器;不删除它:

```bash
docker compose -f docker-compose.prod.yml stop portal

if docker container inspect new-api-old-port >/dev/null 2>&1; then
  docker update --restart=no new-api-old-port >/dev/null
  docker stop new-api-old-port
  test "$(docker inspect new-api-old-port --format '{{.State.Running}}')" = 'false'
```

然后先按 4.3 节运行并验证 Portal PostgreSQL 备份,再按 8.3 节备份 new-api MySQL、
`/opt/new-api/data`、容器 inspect 和两份环境文件。

执行。不能使用登录响应中数百字符的短效 JWT。下列读取方式不会把 token 写入 shell history:

```bash

  --phase=prepare --pricing-snapshot="$PRICING_SNAPSHOT"

  --phase=prepare --pricing-snapshot="$PRICING_SNAPSHOT" --apply
```

`pricing` 只完整合并 `ModelPrice` 的三条价格;`prepare` 只给 `#12` 追加别名/映射。脚本还会拒绝

canonical,且 Portal 仍保持停机,所以不存在别名经旧 Portal 改回 canonical 后按旧低价扣费的窗口。
脚本在项目根目录下的 `.newapi-config-snapshots/` 生成 0600 快照,任一写入/回读失败会按逆序恢复本轮已写内容。

#### 7.5.4 Cutover 与回滚

上述验账全部通过后,在 Mac 先 dry-run,再移除 `#12` 的 canonical:

```bash
node scripts/configure-gpt-image-resolution-skus.mjs \
  --phase=cutover --pricing-snapshot="$PRICING_SNAPSHOT"
node scripts/configure-gpt-image-resolution-skus.mjs \
  --phase=cutover --pricing-snapshot="$PRICING_SNAPSHOT" --apply
```

最终 `/v1/models`、Portal `/models` / `/pricing` 应包含三个固定价别名且不含 canonical;
其他独立图片模型可继续存在。`gpt-image-2-cf` 是另一个上游超分 SKU,脚本刻意不改它的模型或价格;
若产品不希望向客户提供这个独立低价 4K 选项,必须另立变更隐藏/移除,不得悄悄并入本脚本。

任一项不符立即禁用图片组,不允许边放客户流量边修数。手工回滚时先使用脚本输出的快照:

```bash
# 例:先恢复 cutover 快照(重新加回 canonical)
node scripts/configure-gpt-image-resolution-skus.mjs \
  --phase=restore --snapshot='/absolute/path/to/gpt-image-cutover-....json'
node scripts/configure-gpt-image-resolution-skus.mjs \
  --phase=restore --snapshot='/absolute/path/to/gpt-image-cutover-....json' --apply

# 若同时回滚 Portal,再恢复 prepare 快照(移除别名/映射)
node scripts/configure-gpt-image-resolution-skus.mjs \
  --phase=restore --snapshot='/absolute/path/to/gpt-image-prepare-....json' --apply

# 最后恢复 pricing 快照(移除本次新增的三条 ModelPrice)。
# 必须记录这次命令新输出的 gpt-image-restore-....json,
# 不能把下面的 pricing source 快照当成恢复持久化证明。
node scripts/configure-gpt-image-resolution-skus.mjs \
  --phase=restore --snapshot='/absolute/path/to/gpt-image-pricing-....json' --apply
```

`ModelPrice` 恢复后仍是未持久化的 API 状态。在 Mac 对“本轮新生成的 restore 快照”的
`.after.model_price` 求 SHA-256,并在 VPS 用上文同一条 MySQL `SHA2(value,256)` 查询核对。
一致后重启 new-api、等待至少 65 秒,再回 Mac 执行:

```bash
PRICING_RESTORE_RUN='/absolute/path/to/gpt-image-restore-....json'
node scripts/configure-gpt-image-resolution-skus.mjs \
  --phase=verify --snapshot="$PRICING_RESTORE_RUN" --expect=after
```

任何失败路径中,若脚本输出 `ModelPrice durability is still pending`,必须保持图片组禁用。
先在 Mac 对脚本输出的本轮快照 `.before.model_price` 求 SHA-256,再用上文 MySQL 查询核对;
只有两个哈希一致才能重启 new-api、等待 65 秒,然后原样执行脚本输出的
`--expect=before` 命令。任一步未通过前不得声称已回滚。

`restore` 只在当前配置仍等于快照的 after-state 时才写,检测到后续管理员改动会拒绝覆盖。
本方案从未修改 `ModelRatio` / `CompletionRatio`,回滚也不应触碰它们。只有 API 级恢复无法与快照对齐时,
才考虑全库恢复;那会覆盖维护窗口后的用户、Key、余额和日志。

## 8. 备份、恢复与回滚

### 8.1 Portal PostgreSQL 恢复

`gzip -t` 只证明压缩文件没有损坏，不证明 SQL 能成功恢复。恢复会写生产数据，必须先停止写流量、
备份当前状态，并先在隔离数据库演练。以下示例把 plain SQL 恢复到同一 PostgreSQL 容器中的临时库；
正式恢复前应确认备份文件为 `0600`、目标 PostgreSQL 主版本兼容，且不会覆盖维护窗口后的数据：

```bash
set -euo pipefail
ARCHIVE='/opt/backups/silkroadai-portal/portal-YYYYMMDD-HHMMSS.sql.gz'
test "$(stat -c '%a' "$ARCHIVE")" = 600
test -s "$ARCHIVE"
gzip -t "$ARCHIVE"

# 隔离演练：不能连接生产数据库名，也不要在 Portal 运行时执行。
PORTAL_WAS_RUNNING=0
docker ps --format '{{.Names}}' | grep -qx silkroadai-portal && PORTAL_WAS_RUNNING=1 || true
if [ "$PORTAL_WAS_RUNNING" = 1 ]; then
  docker compose --env-file /opt/silkroadai-portal/.env \
    -f /opt/silkroadai-portal/docker-compose.prod.yml stop portal
fi
restore_portal() {
  rc=$?
  docker exec silkroadai-portal-db psql -U portal -d postgres -v ON_ERROR_STOP=1 \
    -c 'DROP DATABASE IF EXISTS portal_restore_check' >/dev/null 2>&1 || true
  if [ "$PORTAL_WAS_RUNNING" = 1 ]; then
    docker compose --env-file /opt/silkroadai-portal/.env \
      -f /opt/silkroadai-portal/docker-compose.prod.yml start portal >/dev/null || rc=$?
  fi
  exit "$rc"
}
trap restore_portal EXIT
docker exec silkroadai-portal-db psql -U portal -d postgres -v ON_ERROR_STOP=1 \
  -c 'DROP DATABASE IF EXISTS portal_restore_check' \
  -c 'CREATE DATABASE portal_restore_check OWNER portal'
gunzip -c "$ARCHIVE" | docker exec -i silkroadai-portal-db \
  psql -v ON_ERROR_STOP=1 -U portal -d portal_restore_check
docker exec silkroadai-portal-db psql -v ON_ERROR_STOP=1 -U portal -d portal_restore_check \
  -c "SELECT to_regclass('public.users'), count(*) FROM public.users" \
  -c 'SELECT count(*) FROM "_prisma_migrations"'
docker exec silkroadai-portal-db psql -U portal -d postgres -v ON_ERROR_STOP=1 \
  -c 'DROP DATABASE portal_restore_check'
if [ "$PORTAL_WAS_RUNNING" = 1 ]; then
  docker compose --env-file /opt/silkroadai-portal/.env \
    -f /opt/silkroadai-portal/docker-compose.prod.yml start portal
fi
trap - EXIT
```

正式恢复必须再次备份故障现场，停止 Portal 写入，并由 operator 明确选择“覆盖现有库”或“恢复到新库
后切换连接串”。不能直接把上面的 `portal_restore_check` 改成生产库名，也不能用 `prisma migrate reset`。

### 8.1.1 新服务器 Portal + new-api PostgreSQL 与 data 一致性备份

Portal 和 new-api 的 PostgreSQL 都是主数据源，`/opt/new-api/data` 保存 new-api 运行所需的文件；Redis
只作缓存，不是恢复源。备份时必须在同一个静止窗口停止 Portal 和 new-api，使用同一 `BACKUP_TAG` 原子
写入并记录 SHA：

```bash
set -euo pipefail
umask 077
BACKUP_TAG="$(date +%Y%m%d-%H%M%S)"
BACKUP_DIR="/opt/backups/new-api/$BACKUP_TAG"
install -d -m 700 "$BACKUP_DIR"
PORTAL_WAS_RUNNING=0
NEWAPI_WAS_RUNNING=0
docker inspect silkroadai-portal > "$BACKUP_DIR/portal.inspect.json"
docker inspect silkroadai-portal-db > "$BACKUP_DIR/portal-db.inspect.json"
docker inspect postgres > "$BACKUP_DIR/postgres.inspect.json"
docker inspect new-api > "$BACKUP_DIR/new-api.inspect.json"
docker inspect redis > "$BACKUP_DIR/redis.inspect.json"
chmod 600 "$BACKUP_DIR"/*.json
docker ps --format '{{.Names}}' | grep -qx silkroadai-portal && PORTAL_WAS_RUNNING=1 || true
docker ps --format '{{.Names}}' | grep -qx new-api && NEWAPI_WAS_RUNNING=1 || true
restore_services() {
  rc=$?
  if [ "$NEWAPI_WAS_RUNNING" = 1 ]; then docker start new-api >/dev/null || rc=$?; fi
  if [ "$PORTAL_WAS_RUNNING" = 1 ]; then docker start silkroadai-portal >/dev/null || rc=$?; fi
  exit "$rc"
}
trap restore_services EXIT
if [ "$PORTAL_WAS_RUNNING" = 1 ]; then docker stop silkroadai-portal >/dev/null; fi
if [ "$NEWAPI_WAS_RUNNING" = 1 ]; then docker stop new-api >/dev/null; fi

install -m 600 /opt/new-api/.env "$BACKUP_DIR/new-api.env"
install -m 600 /opt/silkroadai-portal/.env "$BACKUP_DIR/portal.env"
install -m 600 /opt/deploy-state/new-api-source.sha256 "$BACKUP_DIR/new-api-source.sha256"
install -m 600 /opt/deploy-state/portal-source.sha256 "$BACKUP_DIR/portal-source.sha256"
install -m 600 /opt/silkroadai-portal/deploy/new-api-custom-compose.yml \
  "$BACKUP_DIR/new-api-custom-compose.yml"
install -m 600 /opt/silkroadai-portal/docker-compose.prod.yml \
  "$BACKUP_DIR/portal-compose.yml"
# Portal 和 new-api 都已停止；两个 dump 与 data tar 共用 BACKUP_TAG 和同一维护窗口。
docker exec silkroadai-portal-db sh -lc \
  'PGPASSWORD="$POSTGRES_PASSWORD" pg_dump --format=plain --no-owner -U portal -d silkroadai_portal_prod' \
  | gzip -9 > "$BACKUP_DIR/portal.postgres.sql.gz.tmp"
gzip -t "$BACKUP_DIR/portal.postgres.sql.gz.tmp"
test -s "$BACKUP_DIR/portal.postgres.sql.gz.tmp"
# PGPASSWORD 只在容器内的子进程环境中传递，不把密码放进命令行参数或备份日志。
docker exec postgres sh -lc 'PGPASSWORD="$POSTGRES_PASSWORD" pg_dump --format=custom --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  > "$BACKUP_DIR/new-api.postgres.dump.tmp"
test -s "$BACKUP_DIR/new-api.postgres.dump.tmp"
docker run --rm -v "$BACKUP_DIR:/backup:ro" postgres:15 \
  pg_restore --list /backup/new-api.postgres.dump.tmp >/dev/null
tar -C /opt/new-api -czf "$BACKUP_DIR/new-api-data.tar.gz.tmp" data
tar -tzf "$BACKUP_DIR/new-api-data.tar.gz.tmp" >/dev/null
mv "$BACKUP_DIR/new-api.postgres.dump.tmp" "$BACKUP_DIR/new-api.postgres.dump"
mv "$BACKUP_DIR/new-api-data.tar.gz.tmp" "$BACKUP_DIR/new-api-data.tar.gz"
mv "$BACKUP_DIR/portal.postgres.sql.gz.tmp" "$BACKUP_DIR/portal.postgres.sql.gz"
printf '%s\n' "$BACKUP_TAG" > "$BACKUP_DIR/backup-tag"
docker exec postgres sh -lc 'psql -At -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version()"' \
  > "$BACKUP_DIR/postgres-version.txt"
docker inspect -f '{{.Image}}' postgres > "$BACKUP_DIR/postgres-image.txt"
docker inspect -f '{{.Image}}' new-api > "$BACKUP_DIR/new-api-image.txt"
chmod 600 "$BACKUP_DIR"/*
sha256sum "$BACKUP_DIR/portal.postgres.sql.gz" "$BACKUP_DIR/new-api.postgres.dump" \
  "$BACKUP_DIR/new-api-data.tar.gz" > "$BACKUP_DIR/SHA256SUMS"
```

备份完成后，确认 `SHA256SUMS`、PostgreSQL 版本（`SELECT version()`）、镜像 digest 和 Compose 文件
版本都已归档，再让 trap 按原状态启动容器。备份目录及文件必须分别为 `0700`/`0600`，并复制到加密的
异机存储。不要只备份 Redis 或只打包 `data`；两者与 PostgreSQL 不一致时不能作为可恢复快照。

### 8.1.2 新服务器 new-api 隔离恢复演练

恢复前先在同主版本的临时 PostgreSQL 容器（例如 `postgres:15`，宿主机仅绑定
`127.0.0.1:15432`）和临时 data 目录中验证，不能覆盖 `/opt/new-api/data` 或生产 named volume：

```bash
set -euo pipefail
RESTORE_DIR='/opt/restore/new-api'
RESTORE_ENV='/opt/backups/new-api/YYYYMMDD-HHMMSS/new-api.env'
install -d -m 700 "$RESTORE_DIR/data"
tar -xzf /opt/backups/new-api/YYYYMMDD-HHMMSS/new-api-data.tar.gz -C "$RESTORE_DIR"
tar -tzf /opt/backups/new-api/YYYYMMDD-HHMMSS/new-api-data.tar.gz >/dev/null
sha256sum -c /opt/backups/new-api/YYYYMMDD-HHMMSS/SHA256SUMS
RESTORE_DB_PASSWORD="$(awk -F= '$1 == "POSTGRES_PASSWORD" {sub(/^[^=]*=/, ""); gsub(/^\"|\"$/, ""); print; exit}' "$RESTORE_ENV")"
test -n "$RESTORE_DB_PASSWORD"
RESTORE_REDIS_PASSWORD="$(openssl rand -hex 32)"
restore_cleanup() {
  rc=$?
  docker rm -f new-api-restore >/dev/null 2>&1 || true
  docker rm -f new-api-restore-redis >/dev/null 2>&1 || true
  docker rm -f new-api-restore-pg >/dev/null 2>&1 || true
  docker volume rm new-api-restore-pg >/dev/null 2>&1 || true
  docker network rm new-api-restore-net >/dev/null 2>&1 || true
  exit "$rc"
}
trap restore_cleanup EXIT
# 清理上次被 Ctrl-C/SSH 断开留下的同名隔离资源；这些名称专用于本演练。
docker rm -f new-api-restore >/dev/null 2>&1 || true
docker rm -f new-api-restore-redis >/dev/null 2>&1 || true
docker rm -f new-api-restore-pg >/dev/null 2>&1 || true
docker volume rm new-api-restore-pg >/dev/null 2>&1 || true
docker network rm new-api-restore-net >/dev/null 2>&1 || true
docker network create new-api-restore-net >/dev/null
docker volume create new-api-restore-pg >/dev/null
docker run -d --name new-api-restore-pg \
  --network new-api-restore-net \
  -e POSTGRES_USER=root \
  -e POSTGRES_PASSWORD="$RESTORE_DB_PASSWORD" \
  -e POSTGRES_DB=new-api \
  -p 127.0.0.1:15432:5432 \
  -v new-api-restore-pg:/var/lib/postgresql/data \
  postgres:15 >/dev/null
for _ in $(seq 1 30); do
  docker exec new-api-restore-pg pg_isready -U root -d new-api >/dev/null 2>&1 && break
  sleep 1
done
docker exec new-api-restore-pg pg_isready -U root -d new-api
# 导入 custom-format dump；密码只通过环境变量传给临时客户端。
docker run --rm -v /opt/backups/new-api/YYYYMMDD-HHMMSS:/backup:ro postgres:15 \
  pg_restore --list /backup/new-api.postgres.dump >/dev/null
docker run --rm --network host \
  -e PGPASSWORD="$RESTORE_DB_PASSWORD" \
  -v /opt/backups/new-api/YYYYMMDD-HHMMSS:/backup:ro postgres:15 \
  pg_restore --exit-on-error --no-owner -h 127.0.0.1 -p 15432 -U root -d new-api \
  /backup/new-api.postgres.dump
docker run --rm --network host \
  -e PGPASSWORD="$RESTORE_DB_PASSWORD" postgres:15 \
  psql -h 127.0.0.1 -p 15432 -U root -d new-api -v ON_ERROR_STOP=1 \
  -c 'SELECT count(*) AS users FROM users' \
  -c 'SELECT count(*) AS channels FROM channels'
docker run -d --name new-api-restore-redis --network new-api-restore-net \
  -e REDIS_PASSWORD="$RESTORE_REDIS_PASSWORD" redis:7-alpine \
  sh -lc 'exec redis-server --requirepass "$REDIS_PASSWORD"' >/dev/null
for _ in $(seq 1 30); do

RESTORE_IMAGE='new-api-custom:latest'
```

### 8.3 历史 new-api MySQL 一致性备份

以下仅适用于旧服务器的 MySQL 容器。新服务器使用 PostgreSQL + Redis，按第 0.12 节材料和本节前的
Portal 备份流程执行，不要运行下面的 `mysqldump`。变更旧环境的价目、渠道或镜像前,必须先停 Portal 流量和 `new-api-old-port`。下列命令会再短暂停正式
`new-api`,使 MySQL dump 与 `/opt/new-api/data` 处于同一静止窗口;完成后自动启动正式容器。

```bash
(
  set -euo pipefail
  umask 077

  BACKUP_TAG="$(date +%Y%m%d-%H%M%S)"
  BACKUP_DIR='/opt/backups/new-api'
  install -d -m 700 "$BACKUP_DIR"

  docker inspect new-api > "$BACKUP_DIR/new-api-${BACKUP_TAG}.inspect.json"
  docker inspect new-api-mysql > "$BACKUP_DIR/new-api-mysql-${BACKUP_TAG}.inspect.json"
  if docker container inspect new-api-old-port >/dev/null 2>&1; then
    docker inspect new-api-old-port > "$BACKUP_DIR/new-api-old-port-${BACKUP_TAG}.inspect.json"
  fi
  test -f /root/new-api.env
  install -m 600 /root/new-api.env "$BACKUP_DIR/new-api-${BACKUP_TAG}.env"
  test -f /opt/silkroadai-portal/.env
  install -m 600 /opt/silkroadai-portal/.env "$BACKUP_DIR/portal-${BACKUP_TAG}.env"

  NEWAPI_STOPPED=0
  restart_newapi() {
    if [ "$NEWAPI_STOPPED" = '1' ]; then
      docker start new-api >/dev/null
    fi
  }
  trap restart_newapi EXIT

  docker stop new-api >/dev/null
  NEWAPI_STOPPED=1
  docker exec new-api-mysql sh -lc 'test -n "$MYSQL_DATABASE" && test -n "$MYSQL_ROOT_PASSWORD"'

  SQL_TMP="$BACKUP_DIR/.new-api-${BACKUP_TAG}.sql.gz.tmp"
  DATA_TMP="$BACKUP_DIR/.new-api-data-${BACKUP_TAG}.tar.gz.tmp"
  docker exec new-api-mysql sh -lc \
    'exec mysqldump --single-transaction --routines --triggers -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' \
    | gzip -c > "$SQL_TMP"
  test -s "$SQL_TMP"
  gzip -t "$SQL_TMP"

  test -d /opt/new-api/data
  tar -C /opt/new-api -czf "$DATA_TMP" data
  test -s "$DATA_TMP"
  tar -tzf "$DATA_TMP" >/dev/null

  mv "$SQL_TMP" "$BACKUP_DIR/new-api-${BACKUP_TAG}.sql.gz"
  mv "$DATA_TMP" "$BACKUP_DIR/new-api-data-${BACKUP_TAG}.tar.gz"

  docker start new-api >/dev/null
  NEWAPI_STOPPED=0
  for _ in $(seq 1 30); do
    if curl -fsS --max-time 2 http://172.17.0.1:3000/api/setup >/dev/null; then
      break
    fi
    sleep 1
  done
  curl -fsS --max-time 5 http://172.17.0.1:3000/api/setup >/dev/null
  trap - EXIT

  ls -l "$BACKUP_DIR"/*"${BACKUP_TAG}"*
)
```

`set -euo pipefail` 是必须的:没有 `pipefail` 时 `mysqldump` 失败仍可能由 `gzip` 返回 0,生成能通过
`gzip -t` 但没有 SQL 内容的伪备份。若子 shell 在启动 new-api 前异常退出,`trap` 会尝试恢复;
仍必须人工执行 `docker ps` 和 `/api/setup` 回读。备份验证完成前不得删除 `new-api-old-port`。

### SSH 隧道首个请求成功、加载后台后全部卡死

> **以下为 2026-08/09 旧服务器历史证据**：段落中的“当前”指当时环境，测速与配置验收不能当作
> 新服务器结果。新服务器连接见 [0.9 节](#09-ssh-隧道访问-new-api-后台)，最新取证、切换及回退见
> [2026-10-12 修复报告](../docs/SSH-TUNNEL-REPAIR-2026-10-12.md)。

2026-08-04 在 operator 当前中国电信网络上复现并定位过一次。症状是 `/api/setup` 首次返回 200,
但加载 new-api 的 3.42 MB 主脚本后,后续 curl 虽能连接本地监听却收不到响应。该问题不是 Chrome、
new-api、Docker、SSH forwarding 或 MTU:

- 不经过端口转发、直接让 SSH shell 下发 5 MB 数据时同样卡住,耗时 5 分 32 秒。
- 直接从 VPS Nginx HTTP/80 下载 5 MB 同样超时,证明并非仅 SSH/22 被限制。
- 反方向 Mac -> VPS 上传 5 MB 约 11 秒,故障集中在 VPS -> Mac 下行。
- `ss -tinp` 显示服务端发送数据重传约 17%-28%,CUBIC `cwnd` 塌到 2-4;同时 MSS 1440、PMTU
  1500 正常。路由追踪显示该方向经海外运营商进入中国电信,但仅凭 traceroute 不能断言具体故障跳点。

8 月 4 日的历史测试中，临时切换 BBR 后，同一 SSH 5 MB 下行从 5 分 32 秒降到 8.29 秒，
new-api 3.42 MB 主脚本在新隧道中 3.91 秒完整下载。这些数值不是本次验收结果。

2026-09-11 再次排查时，发现 `/etc/sysctl.d/99-llmroute-bbr.conf` 实际是目录，内嵌配置未按
预期加载，运行值为 `cubic` / `fq_codel`。旧记录“已持久化 BBR + fq”不准确；目录时间早于
本次应用发布，不能据此归因于发布。此次已备份原目录并修成普通配置文件，仅持久化已验证有效的
BBR，保留 `fq_codel` 和全部活动网卡队列，没有运行全局 `sysctl --system`。

同一 110270 字节压缩脚本的三轮交替对照：旧 CUBIC 隧道中位耗时 6.558 秒，独立 BBR 隧道
0.827 秒。正式 3000 隧道重建后中位耗时 0.916 秒，主脚本 978628 字节下载 1.165 秒。
这是当前线路的短时测量，不保证所有页面提速同样倍数。完整证据和回退见
[`docs/SSH-TUNNEL-REPAIR-2026-09-11.md`](../docs/SSH-TUNNEL-REPAIR-2026-09-11.md)。当前配置为:

```text
# /etc/modules-load.d/llmroute-bbr.conf
tcp_bbr

# /etc/sysctl.d/99-llmroute-bbr.conf
net.ipv4.tcp_congestion_control = bbr
```

检查当前状态:

```bash

sysctl net.ipv4.tcp_congestion_control \
```

定位具体 TCP 连接，确认 `ss -ti` 显示 `bbr`，不能仅检查全局默认值。
