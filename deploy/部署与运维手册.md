## 1. 分支与发布规则

三个长期分支的职责固定如下:

| 分支   | 职责       | 允许的操作                                           |
| ------ | ---------- | ---------------------------------------------------- |
| `main` | 上游镜像   | 只同步上游,不做项目自定义修改,不解决项目冲突,不部署  |
| `dev`  | 开发与集成 | 自研开发、合并 `main`、解决冲突、类型检查和完整测试  |
| `prod` | 生产发布   | 只接收测试通过的 `dev` fast-forward,VPS 只部署此分支 |

每次同步上游必须先报告、后执行。报告包括每个提交的北京时间、SHA、行为变化、migration、
环境变量、服务器/Nginx/Cloudflare/安全影响,以及与 `dev` 的差异和冲突预判。固定流程是:

```text
upstream -> main -> 变更报告 -> dev 合并/解决冲突 -> 完整验证
         -> prod fast-forward -> operator 明确安排 -> VPS 手动部署
```

CI 只做检查,不会自动部署。禁止从 `main` 直接上线。

### 2.2 当前容器和网络

| 容器                   | 当前用途             | 宿主机绑定        | 启动方式                                            |
| ---------------------- | -------------------- | ----------------- | --------------------------------------------------- |
| `silkroadai-portal`    | Next.js Portal       | `127.0.0.1:3002`  | `docker-compose.prod.yml` 的 `portal` 服务          |
| `silkroadai-portal-db` | Portal PostgreSQL 16 | `127.0.0.1:5432`  | `docker-compose.prod.yml` 的 `portal-postgres` 服务 |
| `new-api`              | 模型路由与计费       | `172.17.0.1:3000` | 手工 `docker run`                                   |
| `new-api-mysql`        | new-api MySQL 8      | 不发布宿主机端口  | new-api 原有 Docker 网络                            |

关键网络事实:

- new-api 和 MySQL 所在网络:`new-api_new-api-net`。
- Portal 的 compose 也会加入这个 external network,部署前该网络必须存在。
- Portal 仍通过 `NEWAPI_BASE_URL=http://host.docker.internal:3000` 访问 new-api。
- new-api 必须绑定 `172.17.0.1:3000`,不能绑 `127.0.0.1:3000`,否则 Portal 容器访问会被拒绝。
- 不要把 new-api 改成 `0.0.0.0:3000`,否则会扩大公网暴露面。
- new-api 持久化目录:`/opt/new-api/data -> /data`。
- 服务器上可能保留停止状态的 `new-api-old-port` 回退容器。确认新容器和备份稳定前不要误删。

`docker-compose.prod.yml` 还包含上游的 `portal-api-1..3` 和 `seedance-portal`,但已经用 Compose
profiles 隔离:

- `portal-api-1..3` 属于 `api-replicas` profile。
- `seedance-portal` 属于 `seedance` profile。
- 默认不启用 profile 时,只会启动主站 Portal 及其 PostgreSQL 依赖。

这台服务器当前只部署主站 Portal,日常发布仍显式指定 `portal`,让操作目标一眼可见:

```bash
docker compose -f docker-compose.prod.yml up -d portal
```

如未来明确部署上游可选服务,必须显式启用对应 profile,例如
`docker compose -f docker-compose.prod.yml --profile api-replicas up -d`。不要在当前 LLmRoute
服务器启用未配置、未验收的 profile。

```bash
cd /opt/silkroadai-portal
pwd
ls -l .env .env.prod.example
```

### 3.3 构建时变量

所有 `NEXT_PUBLIC_*` 都可能被 Next.js 编译进客户端产物。修改后必须重新 build,仅重启容器不可靠。
`docker-compose.prod.yml` 会从同目录 `.env` 读取以下公开变量,并作为 build args 传给 Dockerfile:

```env
APP_URL="https://llmroute.club"
NEXT_PUBLIC_APP_URL="https://llmroute.club"
NEXT_PUBLIC_API_URL="https://api.llmroute.club"
NEXT_PUBLIC_IMAGE_URL="https://images.llmroute.club"
NEXT_PUBLIC_SUPPORT_EMAIL="support@llmroute.club"
NEXT_PUBLIC_SUPPORT_WECHAT="LLmRoute"
```

Dockerfile 对这些变量也提供 LLmRoute 默认值,避免直接构建时回落到上游旧域名。标准生产构建不再需要逐个手写
`--build-arg`;先核对 `.env`,再执行:

```bash
docker compose -f docker-compose.prod.yml build portal
docker compose -f docker-compose.prod.yml up -d portal
```

纯运行时变量修改后可执行 `up -d portal`;只要改了代码或 `NEXT_PUBLIC_*`,就按上面的 build + up 两步执行。

### 3.4 不可轮换项

- `PORTAL_OSS_ENC_KEY` 用于解密客户已保存的 OSS Secret。投产后不能随意更换,否则历史配置无法解密。
- new-api 后台“系统访问令牌”的生成操作是 rotate。重新生成会立即让旧 `NEWAPI_ADMIN_TOKEN` 失效。
- 数据库密码修改需要同时处理 `.env`、PostgreSQL 用户和现有 volume,不能只改模板。

## 6. Nginx 与 Cloudflare

### 6.1 当前证书

```text
/etc/nginx/ssl/llmroute.club.pem
/etc/nginx/ssl/llmroute.club.key
```

私钥权限必须是 600。证书为 Cloudflare Origin CA,有效期核验:

```bash
chmod 600 /etc/nginx/ssl/llmroute.club.key
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -noout -subject -issuer -dates -ext subjectAltName
```

证书和私钥匹配核验:

```bash
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -pubkey -noout \
  | openssl pkey -pubin -outform der | sha256sum
openssl pkey -in /etc/nginx/ssl/llmroute.club.key -pubout \
  | openssl pkey -pubin -outform der | sha256sum
```

两个 SHA-256 必须完全相同。

### 6.2 当前主站路由要求

Nginx 中 `llmroute.club` 和 `www.llmroute.club` 应共同反代 `127.0.0.1:3002`,HTTP 跳 HTTPS。
仓库基线模板为 `deploy/nginx/llmroute-web.conf`,生产安装路径为
`/etc/nginx/conf.d/llmroute.club.conf`。不要只在服务器临时 `sed`,否则配置无法审计和复现。
该模板的 access log 只记录 `$uri`,不记录 query string,避免 OAuth code、密码重置/邮箱验证 token 和
支付回调签名落盘。
`/image-adapter/*` 是 new-api 的内部上游适配器,主站 Nginx 必须对公网返回 404。若未来启用该图片渠道,
new-api 的 Base URL 使用共享 Docker 网络地址
`http://silkroadai-portal:3002/image-adapter/ominiapi`,上游 Key 只保存在 new-api 渠道配置中;禁止改成
`https://llmroute.club/image-adapter/ominiapi` 绕公网调用。
修改任何 Nginx 配置后统一执行:

```bash
nginx -t && systemctl reload nginx
```

Cloudflare DNS 的 apex 与 `www` 记录都应指向 `82.29.71.122` 并开启橙云。SSL/TLS 模式保持
**Full (strict)**,不要使用 Flexible。

### 6.3 `api.llmroute.club` 独立入口

固定路径策略如下:

- 只有 `/v1/*` 和 `/v1beta/*` 对公网开放,两者都先进入 Portal `127.0.0.1:3002`。
- 不把 API 子域直接代理到 new-api,否则会绕过 Gemini 图片转换、请求体守门、Codex clamp、日志捕获和
  SSE keep-alive 等 Portal 能力。
- `/login`、`/admin/*`、支付和 Portal 内部 API 在该 hostname 一律返回 JSON 404;管理入口只留主站域名。
- SSE 关闭 Nginx buffering/cache,长图片/视频请求 read/send timeout 为 650 秒,请求体上限 100 MB。
- access log 只记录 `$uri`,不记录 `$request_uri`,避免 Gemini SDK 的 `?key=` 凭据写入源站日志。

仓库模板是 `deploy/nginx/llmroute-api.conf`。部署前先查看并备份真实配置:

```bash
nginx -T 2>&1 | grep -E '^# configuration file|listen|server_name|ssl_certificate|proxy_pass|client_max_body_size|proxy_(buffering|request_buffering|read_timeout)'
ls -la /etc/nginx/conf.d/

umask 077
tar -C /etc/nginx -czf "/root/nginx-config-before-api.$(date +%Y%m%d-%H%M%S).tar.gz" nginx.conf conf.d
```

拉取本次 `prod` 后同时安装主站与 API 模板。主站模板只在现有配置基础上显式补入 `www`;API 模板
新增独立 virtual host。`nginx -t` 失败时不得 reload:

```bash
install -o root -g root -m 0644 \
  /opt/silkroadai-portal/deploy/nginx/llmroute-web.conf \
  /etc/nginx/conf.d/llmroute.club.conf
install -o root -g root -m 0644 \
  /opt/silkroadai-portal/deploy/nginx/llmroute-api.conf \
  /etc/nginx/conf.d/llmroute-api.conf
nginx -t && systemctl reload nginx
```

Cloudflare 必须同时满足:

1. 显式 `A api -> 82.29.71.122`,代理状态为橙云;不要只依赖 wildcard 记录。
2. SSL/TLS 模式为 **Full (strict)**。
3. Cache Rules 中 `Hostname equals api.llmroute.club` 设置 **Bypass cache**;API/SSE 不允许缓存。

安装后按第 5.3 节验收,并确认日志没有查询参数泄漏。这里使用的是无效测试串,不是真 Key:

```bash
curl -k -sS -o /dev/null \
  --resolve api.llmroute.club:443:127.0.0.1 \
  'https://api.llmroute.club/v1beta/models/test:generateContent?key=redaction-smoke'
if grep -F 'redaction-smoke' /var/log/nginx/api.llmroute.club.access.log; then
  echo 'FAIL: API query string leaked into access log' >&2
  exit 1
fi
```

紧急回滚该 virtual host:

```bash
mv /etc/nginx/conf.d/llmroute-api.conf /etc/nginx/conf.d/llmroute-api.conf.disabled
nginx -t && systemctl reload nginx
```

这只回滚 Nginx 路由,会让该域名重新落入 default virtual host;随后仍需按 Git 发布流程修复,不能把
default host 当作长期 API 入口。

不要在 master 仍运行时删除 control socket。只有 `ssh -O check` 已确认 master 不存在且 socket 是陈旧文件时,
才将旧 socket 改名留档后重建隧道。

未配置该别名或本地 3000 端口冲突时,可使用独立的 18082 端口:

```bash
ssh -4 -f -N -T -C \
  -i "$HOME/.ssh/llmroute_ed25519" \
  -o IdentitiesOnly=yes \
  -o IPQoS=none \
  -o TCPKeepAlive=yes \
  -o ServerAliveInterval=15 \
  -o ServerAliveCountMax=4 \
  -o ExitOnForwardFailure=yes \
  -o ControlMaster=no \
  -L 127.0.0.1:18082:172.17.0.1:3000 \
  root@82.29.71.122

curl --max-time 10 http://127.0.0.1:18082/api/setup
```

返回 `success:true` 后浏览器打开 `http://127.0.0.1:18082/`。`-f` 会让隧道在认证完成后进入后台;
查看和停止时只操作该监听 PID,不要用会误杀其他 SSH 会话的宽泛 `pkill`:

```bash
lsof -nP -iTCP:18082 -sTCP:LISTEN
kill "$(lsof -tiTCP:18082 -sTCP:LISTEN)"
```

如果已有旧隧道,先停止旧监听再重建。服务器切换拥塞控制算法后,已经建立的 SSH 连接不会自动采用
新算法,也必须重建。

### 7.4 new-api 技术计费单位迁移(500000 quota = ¥1)

本节是一次性生产迁移。只有 operator 明确安排维护窗口后才能执行。代码发布与参数切换必须分开:
先发布兼容代码并保持生产旧值不变,确认正常后再进入停写窗口。不得只修改
`USD_TO_CNY_RATE`,否则旧余额会缩小 7.2 倍;也不得只放大余额而不重同步 Portal 目录模型,否则这些
模型会少扣 7.2 倍。

迁移后的固定不变量:

- new-api `QuotaPerUnit=500000` 保持不变。
- Portal `NEWAPI_QUOTA_PER_USD=500000`、`USD_TO_CNY_RATE=1`、
  `REAL_USD_TO_CNY_RATE=7.2`。
- 客户充值 ¥1 增加 500000 raw quota;500000 raw quota 在 Portal 显示为 ¥1。
- 真实美元展示为 `人民币 ÷ REAL_USD_TO_CNY_RATE`,真实汇率不参与人民币扣费。
- 公共 `GroupRatio`、内部用户组、`GroupGroupRatio` 专属规则和 Token.group 都不因本迁移改变。

#### 7.4.1 发布兼容代码,暂不切参数

按第 4 节发布包含计费单位兼容修复的代码,但服务器 `.env` 暂时继续保持原值
`USD_TO_CNY_RATE=7.2`,且暂不新增 `REAL_USD_TO_CNY_RATE`。新代码在该组合下行为中性。确认 Portal、
充值、余额和 new-api 链路正常后,再预约低流量维护窗口。

#### 7.4.2 停写与三份快照

维护开始后先停止 Portal,阻断 `/v1` 调用、充值回调和后台写操作:

```bash
cd /opt/silkroadai-portal
docker compose -f docker-compose.prod.yml stop portal
curl -sS -o /dev/null -w '%{http_code}\n' https://api.llmroute.club/v1/models
```

第二条应不再返回正常业务响应。随后依次完成并校验三份快照:

1. 按 4.3 节运行 `scripts/backup-db.sh`,并执行 `gzip -t`。
2. 复制当前 `.env` 为 0600 的带时间戳备份。
3. 对 `new-api-mysql` 做 `--single-transaction` 全库备份,并另存以下可读快照:
   Portal 所有已映射的 `newapi_user_id`;每个用户的 `id/quota/used_quota/group`;完整
   option 响应(至少核对 `ModelRatio`、`CompletionRatio`、`GroupRatio`、`GroupGroupRatio`、
   `UserUsableGroups`);Portal 当前所有已启用的目录模型、人民币价格、档次和 upstream model 映射。

MySQL 备份命令在容器已设置 `MYSQL_DATABASE` / `MYSQL_ROOT_PASSWORD` 时可用;任何变量为空都必须停止:

```bash
MIGRATION_TAG="$(date +%Y%m%d-%H%M%S)"
install -d -m 700 /opt/backups/new-api
docker exec new-api-mysql sh -lc 'test -n "$MYSQL_DATABASE" && test -n "$MYSQL_ROOT_PASSWORD"'
docker exec new-api-mysql sh -lc \
  'exec mysqldump --single-transaction --routines --triggers -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' \
  | gzip > "/opt/backups/new-api/new-api-${MIGRATION_TAG}.sql.gz"
chmod 600 "/opt/backups/new-api/new-api-${MIGRATION_TAG}.sql.gz"
gzip -t "/opt/backups/new-api/new-api-${MIGRATION_TAG}.sql.gz"
```

不要把 access token、`.env` 内容或完整用户 JSON 打到终端/聊天。快照目录和文件均用 0600/0700。

#### 7.4.3 计算并覆盖余额

对每个 Portal 映射用户使用停写后快照的 `old_quota` 和 `old_used_quota` 计算:

```text
target_quota = round((old_quota + old_used_quota) × 7.2 - old_used_quota)
             = round(old_quota × 7.2 + old_used_quota × 6.2)
```

含义是先按旧口径还原累计人民币额度,再按新口径扣回历史真实消费。通过 new-api
`POST /api/user/manage` 的 `add_quota + override` 写入 `target_quota`;禁止直接 `PUT /api/user/` 改 quota,
以免触发用户字段覆盖。每写一个用户立即 `GET /api/user/{id}` 回读并核对 quota、used_quota 和 group。
请求体固定为
`{"id": <new-api user id>, "action": "add_quota", "mode": "override", "value": <target_quota>}`。

2026-08-24 只读审计时的参考值如下;执行前必须重新快照,若值变化则按新快照重算,不能照抄旧数字:

| new-api user | 审计时旧余额 quota | 审计时 used_quota |             参考 target_quota |
| ------------ | -----------------: | ----------------: | ----------------------------: |
| 6            |      6,848,292,597 |       235,874,067 |                50,770,125,914 |
| 12           |            347,222 |                 0 | 2,500,000（按原 ¥5 调整记录） |
| 13           |            347,222 |                 0 | 2,500,000（按原 ¥5 调整记录） |

其余审计时余额和用量均为 0。普通客户历史调用为 0;唯一历史调用用户是 superadmin 测试账号,因此该次
迁移不涉及普通客户退款。若执行前出现普通客户调用,必须重新做逐用户账务审计后再继续。

#### 7.4.4 切换环境变量与模型倍率

编辑生产 `.env` 为:

```env
NEWAPI_QUOTA_PER_USD=500000
USD_TO_CNY_RATE=1
REAL_USD_TO_CNY_RATE=7.2
```

然后在 new-api 后台“系统设置 → 计费与支付 → 分组定价 → 切换到 JSON”中,基于快照完整合并配置。
只更新 Portal 目录管理的模型,不能覆盖其他模型。2026-08-24 审计时只有以下两项:

- `claude-fable-5`: `ModelRatio` 从 `0.694444` 改为 `5`,其 `CompletionRatio` 保持 `5`。
- `kimi-k3`: `ModelRatio` 从 `1.388889` 改为 `10`,其 `CompletionRatio` 保持 `5`。
- 非 Portal 目录管理模型保持原倍率;`GroupRatio`、`GroupGroupRatio`、`UserUsableGroups` 不改。

执行前必须与 7.4.2 的最新 Portal 目录快照再次比对。若已启用目录模型不再只有这两项,停止迁移并为
每个新增模型补齐新口径倍率清单;chat 模型按
`ModelRatio = 输入人民币价 ÷ (2 × 该档 GroupRatio)` 计算(`2` 是新口径下 100 万 quota 的人民币值),
按张模型也必须按新口径重算 `ModelPrice`。不能把“审计时只有两项”当作永久假设。

保存后重新读取完整 option,逐项确认其他模型和其他用户的规则仍在。再清空 Portal quota 缓存:

```bash
docker exec -i silkroadai-portal-db psql -U portal silkroadai_portal_prod \
  -c 'UPDATE users SET newapi_quota_cache = NULL, newapi_used_quota_cache = NULL, newapi_cached_at = NULL WHERE newapi_user_id IS NOT NULL;'
```

最后按 4.4 节重建/启动 Portal。不得启用 `api-replicas` 或 `seedance` profile。

#### 7.4.5 验收与停止条件

启动后先用 superadmin 测试账号做受控小额验证,普通客户继续保持无流量:

1. Portal 余额人民币值与迁移清单一致;美元值约为人民币值除以 7.2。
2. 管理员充值 ¥1 时,new-api 用户余额精确增加 500000 quota。
3. `claude-fable-5` 与 `kimi-k3` 的同类请求扣费符合目录人民币价格;new-api 日志 raw quota 与 Portal
   人民币显示满足 `Portal ¥ = raw quota ÷ 500000`。
4. 未由 Portal 目录管理的模型做一笔样例,确认原 ModelRatio 未被覆盖。
5. 专属倍率用户的 `User.group`、旧 Key 和新 Key 的 Token.group 均未改变,且 `GroupGroupRatio` 仍命中。

任一余额、倍率、专属规则或模型价格不符,立即停止测试流量并回滚,不能边开放客户流量边修数。

#### 7.4.6 回滚

回滚也必须先停止 Portal。按快照逐个用 `/api/user/manage` `override` 恢复原 quota,完整恢复迁移前
`ModelRatio` / `CompletionRatio` option,恢复 `.env` 备份(`USD_TO_CNY_RATE=7.2`,删除新增的
`REAL_USD_TO_CNY_RATE`),再次清空 Portal quota 缓存并重启。逐个回读验证后才能恢复流量。

只有 API 级回滚失败或数据已无法与快照一致时,才考虑恢复 new-api MySQL 全库备份;全库恢复会覆盖维护
窗口后的所有 new-api 状态,必须保持停写并先再次备份故障现场。代码本身兼容旧参数,通常无需回滚代码。

### 7.5 图片分辨率按张计费

生产官方 `new-api v1.0.0-rc.23` 不支持按 1K/2K/4K 分别计价。LLmRoute 修改版以官方提交
`0ab02020603d22e5613bc4cf46bfab06f8567769` 为基线,版本固定为
`v1.0.0-rc.23-llmroute.1`;只移植图片分辨率计费,不能部署供应商包含其他二开功能的整仓 `main`。

修改版受 AGPL-3.0 约束。部署前必须先公开完整对应源码和构建文件,并确认以下地址对未登录访问者返回 200:

```text
https://github.com/Curry1024Bytes/new-api/tree/v1.0.0-rc.23-llmroute.1
```

源码未公开、tag 与镜像 commit 不一致、工作区不干净或 release 测试未通过时不得部署。公开仓库中严禁包含
`.env`、渠道密钥、数据库、备份或生产日志。

#### 7.5.1 当前生产计费公式与配置值

固定不变量:

- new-api `QuotaPerUnit=500000`;Portal `NEWAPI_QUOTA_PER_USD=500000`、`USD_TO_CNY_RATE=1`。
- `图片模型` 公共 `GroupRatio=0.2`;当前 `GroupGroupRatio` 没有覆盖“客户组 -> 图片模型”规则。
- 客户人民币扣费 = `ImageResolutionPrice[档位] × 有效组倍率 × 实际成功图片数`。
- 上游充值 `1:10` 只用于采购成本换算,不能写进 `GroupRatio`、渠道倍率或价格乘数。

因此,目标客户价为 1K ¥1/张、2K ¥1.5/张、4K ¥2/张时,后台基准价必须除以 `0.2`,填写:

```json
{
    "gpt-image-2": {
        "1K": 5,
        "2K": 7.5,
        "4K": 10
    }
}
```

当有效图片组倍率仍为 `0.2` 时,不能直接填客户价 `1/1.5/2`;否则客户实际只会扣
`0.2/0.3/0.4` 元。

保存路径为 new-api 后台“系统设置 -> 计费与支付 -> 分组定价”的“图片分辨率定价”。每个模型必须同时有
`1K`、`2K`、`4K` 三档。查价使用客户请求中的原始模型名,渠道 `model_mapping` 不会自动合并别名;新增
客户可见别名时必须单独加一项。`gpt-image-2-cf`、`grok-imagine-image` 当前仍是固定按次 SKU,不要放进
分辨率价表,继续由 `ModelPrice` 计费。

若以后新增命中 `图片模型` 的 `GroupGroupRatio` 专属规则,上式中的有效组倍率会被专属值替代。不能继续
机械沿用 `5/7.5/10`,必须按 `后台基准价 = 目标客户单价 / 有效组倍率` 重新计算并做真实扣费验证。

## 8. 备份、恢复与回滚

### 8.1 Portal PostgreSQL 恢复

恢复会写生产数据,必须先停止写流量并再次备份现状。基本命令参考:

```bash
gunzip -c /opt/backups/silkroadai-portal/portal-YYYYMMDD-HHMMSS.sql.gz \
  | docker exec -i silkroadai-portal-db psql -U portal silkroadai_portal_prod
```

正式恢复前要确认备份完整、目标库状态、是否需要清库以及 migration 兼容性,不能直接照抄执行。

### 8.2 代码回滚

首选做法是在 `dev` 创建 revert、跑完整测试、fast-forward 到 `prod`,再按标准流程部署。紧急情况下可在
服务器临时 checkout 已知正常 SHA 并重建,但必须记录 SHA,事后恢复到 `prod`:

```bash
git switch --detach <KNOWN_GOOD_SHA>
docker compose -f docker-compose.prod.yml build portal
docker compose -f docker-compose.prod.yml up -d portal
```

Prisma migration 是 forward-only。代码回滚不会自动回滚 schema;涉及不兼容 migration 时必须制定数据库
恢复方案,不要用 `git reset --hard` 或 `prisma migrate reset` 处理生产事故。

## 9. 常见故障

### Portal 内部正常,公网超时

内部 200 而公网失败通常在 Nginx、云安全组、Cloudflare DNS 或 SSL 模式。

### Portal 连不上 new-api

```bash
curl -sS http://172.17.0.1:3000/api/setup

  "fetch('http://host.docker.internal:3000/api/setup').then(r=>console.log(r.status)).catch(console.error)"
```

重点确认 new-api 绑定 `172.17.0.1:3000`,Portal compose 的 `extra_hosts` 和网络 `gw_priority` 未被删除。

### DNS 解析失败导致 `dnf` 不可用

服务器曾出现公网 IP 可达但域名无法解析。当前连接名通常是 `System eth0`,恢复基线:

```bash
CONN="$(nmcli -t -f NAME con show --active | head -n1)"
nmcli con mod "$CONN" ipv4.ignore-auto-dns yes ipv4.dns "1.1.1.1 8.8.8.8"
nmcli con mod "$CONN" ipv6.ignore-auto-dns yes
nmcli con up "$CONN"
getent hosts mirrors.almalinux.org
```

### SSH 偶发超时或被关闭

```bash
ssh -4 \
  -i "$HOME/.ssh/llmroute_ed25519" \
  -o IdentitiesOnly=yes \
  -o IPQoS=none \
  root@82.29.71.122
```

2026-08-04 已完成 SSH key-only 加固。有效配置位于
`/etc/ssh/sshd_config.d/00-llmroute-hardening.conf`:

```text
PermitRootLogin prohibit-password
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
MaxAuthTries 3
LoginGraceTime 30
```

原生 OpenSSH 和 Xterminal 已验证可用;FinalShell 4.6.5 使用相同 RSA key 仍在 preauth 阶段断开,
属于客户端兼容/配置问题,不要因此重新开放服务器密码登录或全局启用旧 `ssh-rsa` 算法。主机 ED25519
指纹为 `SHA256:ZcqH0BmGvCJ33HsAiTkuFT0cLENcM2UDdz3lzVwThB0`,首次使用新客户端时必须先核对再保存。

`fail2ban` 配置位于 `/etc/fail2ban/jail.d/sshd.local`:10 分钟内失败 5 次先封 1 小时,重复触发按 2 倍
递增,最长 24 小时。检查状态:

```bash
systemctl is-active sshd fail2ban
fail2ban-client status sshd
sshd -T | grep -Ei \
  'permitrootlogin|pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|maxauthtries|logingracetime'
```

服务器曾累计观察到 2,236 次公网失败尝试。私钥不得上传仓库或聊天;丢失全部授权私钥时,只能通过
云厂商控制台恢复。修改 sshd 前仍必须保留一个已登录会话,并先运行 `sshd -t`。

### SSH 隧道首个请求成功、加载后台后全部卡死

2026-08-04 在 operator 当前中国电信网络上复现并定位过一次。症状是 `/api/setup` 首次返回 200,
但加载 new-api 的 3.42 MB 主脚本后,后续 curl 虽能连接本地监听却收不到响应。该问题不是 Chrome、
new-api、Docker、SSH forwarding 或 MTU:

- 不经过端口转发、直接让 SSH shell 下发 5 MB 数据时同样卡住,耗时 5 分 32 秒。
- 直接从 VPS Nginx HTTP/80 下载 5 MB 同样超时,证明并非仅 SSH/22 被限制。
- 反方向 Mac -> VPS 上传 5 MB 约 11 秒,故障集中在 VPS -> Mac 下行。
- `ss -tinp` 显示服务端发送数据重传约 17%-28%,CUBIC `cwnd` 塌到 2-4;同时 MSS 1440、PMTU
  1500 正常。路由追踪显示该方向经海外运营商进入中国电信,但仅凭 traceroute 不能断言具体故障跳点。

服务器现已启用 BBR。临时切换后同一 SSH 5 MB 下行从 5 分 32 秒降到 8.29 秒,new-api 3.42 MB
主脚本在新隧道中 3.91 秒完整下载。持久配置为:

```text
# /etc/modules-load.d/llmroute-bbr.conf
tcp_bbr

# /etc/sysctl.d/99-llmroute-bbr.conf
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
```

检查当前状态:

```bash
lsmod | grep '^tcp_bbr'
sysctl net.ipv4.tcp_congestion_control \
  net.ipv4.tcp_available_congestion_control \
  net.core.default_qdisc

# 将 IP 换成 operator 当前公网 IP;关注 bytes_retrans、cwnd 和 bbr 字样
ss -tinp state established dst <OPERATOR_PUBLIC_IP>
```

预期为 `tcp_congestion_control = bbr`、`default_qdisc = fq`,新建连接的 `ss -ti` 输出以 `bbr`
开头。线路本身仍可能丢包,BBR 是已验证的缓解措施;若再次退化,先重新取证,不要继续随机换本地端口。
