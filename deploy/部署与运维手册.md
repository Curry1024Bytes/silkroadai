## 1. 分支与发布规则

三个长期分支的职责固定如下:

| 分支   | 职责       | 允许的操作                                           |
| ------ | ---------- | ---------------------------------------------------- |
| `main` | 上游镜像   | 只同步上游,不做项目自定义修改,不解决项目冲突,不部署  |
| `dev`  | 开发与集成 | 自研开发、合并 `main`、解决冲突、类型检查和完整测试  |
| `prod` | 生产发布   | 只接收测试通过的 `dev` fast-forward,VPS 只部署此分支 |

每次同步上游必须先报告、后执行。报告包括每个提交的北京时间、SHA、行为变化、migration、
环境变量、服务器/Nginx/Cloudflare/安全影响,以及与 `dev` 的差异和冲突预判。固定流程是:

```text
upstream -> main -> 变更报告 -> dev 合并/解决冲突 -> 完整验证
         -> prod fast-forward -> operator 明确安排 -> VPS 手动部署
```

CI 只做检查,不会自动部署。禁止从 `main` 直接上线。

### 2.2 当前容器和网络

| 容器                   | 当前用途             | 宿主机绑定        | 启动方式                                            |
| ---------------------- | -------------------- | ----------------- | --------------------------------------------------- |
| `silkroadai-portal`    | Next.js Portal       | `127.0.0.1:3002`  | `docker-compose.prod.yml` 的 `portal` 服务          |

关键网络事实:

- new-api 和 MySQL 所在网络:`new-api_new-api-net`。
- Portal 的 compose 也会加入这个 external network,部署前该网络必须存在。
- Portal 仍通过 `NEWAPI_BASE_URL=http://host.docker.internal:3000` 访问 new-api。
- new-api 必须绑定 `172.17.0.1:3000`,不能绑 `127.0.0.1:3000`,否则 Portal 容器访问会被拒绝。
- 不要把 new-api 改成 `0.0.0.0:3000`,否则会扩大公网暴露面。
- new-api 持久化目录:`/opt/new-api/data -> /data`。
- 服务器上可能保留停止状态的 `new-api-old-port` 回退容器。确认新容器和备份稳定前不要误删。

当前 `docker-compose.prod.yml` 还包含上游的 `portal-api-1..3` 和 `seedance-portal`。
这台服务器当前只部署主站 Portal,所以日常发布命令必须显式指定 `portal`:

```bash
docker compose -f docker-compose.prod.yml up -d portal
```

**不要执行不带服务名的 `docker compose ... up -d --build`**,否则可能同时启动不属于当前方案的额外服务。

## 3. 生产配置

### 3.1 文件规则

| 文件                 | 是否进 Git | 用途                      |
| -------------------- | ---------- | ------------------------- |
| `.env.local.example` | 是         | 本地开发模板              |
| `.env.prod.example`  | 是         | 生产配置模板,不含真实密钥 |
| `.env`               | 否         | 服务器真实生产配置        |

首次部署才执行:

```bash
cd /opt/silkroadai-portal
cp .env.prod.example .env
chmod 600 .env
vim .env
```

滚动更新时**绝不能用模板覆盖已有 `.env`**。拉代码不会覆盖被 Git ignore 的 `.env`,只需根据模板 diff
补新增变量。查看或编辑真实配置前先进入正确目录:

```bash
cd /opt/silkroadai-portal
pwd
ls -l .env .env.prod.example
vim .env
```

### 3.2 必填配置组

以下只列变量名和约束,不在文档写真实 secret:

- 数据库:`DATABASE_URL`、`POSTGRES_PASSWORD`,两处密码必须一致,host 必须是 `portal-postgres:5432`。
- new-api:`NEWAPI_BASE_URL`、`NEWAPI_ADMIN_TOKEN`、`NEWAPI_ADMIN_USER_ID`。
- Portal 认证:`PORTAL_JWT_SECRET`、`ADMIN_TOKEN`、`PORTAL_OSS_ENC_KEY`。
- 域名:`APP_URL`、`NEXT_PUBLIC_APP_URL`、`BRAND_COOKIE_DOMAIN`。
- OAuth:`GOOGLE_OAUTH_*`、`GITHUB_OAUTH_*`。
- 支付:`PAYMENT_PROVIDERS`、`ENABLED_PAYMENT_TYPES`、`EASY_PAY_*`。

生产固定公开值:

```env
NEWAPI_BASE_URL="http://host.docker.internal:3000"
APP_URL="https://llmroute.club"
NEXT_PUBLIC_APP_URL="https://llmroute.club"
BRAND_COOKIE_DOMAIN=".llmroute.club"
NEXT_PUBLIC_SUPPORT_WECHAT="LLmRoute"

GOOGLE_OAUTH_REDIRECT_URI="https://llmroute.club/api/auth/oauth/google/callback"
GITHUB_OAUTH_REDIRECT_URI="https://llmroute.club/api/auth/oauth/github/callback"

PAYMENT_PROVIDERS=easypay
ENABLED_PAYMENT_TYPES=alipay,wxpay
EASY_PAY_API_BASE="https://zpayz.cn"
EASY_PAY_NOTIFY_URL="https://llmroute.club/api/easy-pay/notify"
EASY_PAY_RETURN_URL="https://llmroute.club/pay/result"
PRODUCT_NAME="LLmRoute 余额充值"
```

Google/GitHub Client Secret、`EASY_PAY_PKEY` 和 `NEWAPI_ADMIN_TOKEN` 只能填服务器 `.env`,不得提交 Git,
也不要在聊天或终端截图中打印。

### 3.3 构建时变量

所有 `NEXT_PUBLIC_*` 都可能被 Next.js 编译进客户端产物。修改后必须重新 build,仅重启容器不可靠。
本项目这次特别涉及:

```env
NEXT_PUBLIC_SUPPORT_WECHAT="LLmRoute"
```

Dockerfile 的 `APP_URL` 是 build arg。为避免 sitemap/robots 使用继承自上游的旧默认域名,生产构建必须显式传入:

```bash
docker compose -f docker-compose.prod.yml build \
  --build-arg APP_URL=https://llmroute.club portal
docker compose -f docker-compose.prod.yml up -d portal
```

纯运行时变量修改后可执行 `up -d portal`;只要改了代码或 `NEXT_PUBLIC_*`,就按上面的 build + up 两步执行。

### 3.4 不可轮换项

- `PORTAL_OSS_ENC_KEY` 用于解密客户已保存的 OSS Secret。投产后不能随意更换,否则历史配置无法解密。
- new-api 后台“系统访问令牌”的生成操作是 rotate。重新生成会立即让旧 `NEWAPI_ADMIN_TOKEN` 失效。
- 数据库密码修改需要同时处理 `.env`、PostgreSQL 用户和现有 volume,不能只改模板。

## 4. 标准发布流程

### 4.1 本地发布门

在 Mac 仓库执行:


确认 `dev` 包含要发布的内容且测试通过后,只允许 fast-forward `prod`:

```bash
git merge-base --is-ancestor prod dev
git switch prod
git merge --ff-only dev
git push origin prod
git switch dev
```

如果 `--ff-only` 失败,停止并分析分支历史,不要强推、不要重写 `main`。

### 4.2 登录服务器并做发布前检查

```bash

git log -1 --oneline
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

- external network `new-api_new-api-net` 存在。
- `.env` 已备份且权限为 600。

```bash
cp -a .env ".env.bak.$(date +%Y%m%d-%H%M%S)"
chmod 600 .env
```

```bash
cd /opt/silkroadai-portal
```

### 5.3 OAuth

```bash
curl -sS -o /dev/null -D - https://llmroute.club/api/auth/oauth/google/start \
  | grep -iE 'HTTP/|^location:'
curl -sS -o /dev/null -D - https://llmroute.club/api/auth/oauth/github/start \
  | grep -iE 'HTTP/|^location:'
```

分别应 302 到 `accounts.google.com` 和 `github.com/login/oauth/authorize`。最终验收必须在浏览器各登录一次,
不能只看 302。失败时看:

```bash
docker logs --since=10m silkroadai-portal 2>&1 \
  | grep -Ei 'oauth|account-link|provision|new-api|error|failed'
```

当前兼容策略:优先使用 new-api 登录响应体中的 `data.access_token`;旧版本只返回 `session=` cookie 时才走
legacy fallback。不要把 `new_api_refresh` cookie 当 session。此策略已通过 Google 和 GitHub 真实开户验证。

### 5.4 支付

自动检查只能确认路由,最终必须做一笔受控的小额真实支付:

1. 登录测试账号,打开 `/pay`。
2. 发起最低金额充值并选择支付宝。
3. 确认进入 zpayz 收银台。
4. 支付后确认回到 `/pay/result`。
5. 在 `/balance` 确认余额增加且只入账一次。
6. 检查日志没有签名失败或重复入账异常。

```bash
docker logs --since=15m silkroadai-portal 2>&1 \
  | grep -Ei 'easy-pay|notify|recharge|signature|error|failed'
```

zpayz 异步通知要求返回纯字符串 `success`;重复通知由订单状态机幂等处理。商户 PID 可以记录在模板,
商户 KEY 只能保存在服务器 `.env`。

## 6. Nginx 与 Cloudflare

### 6.1 当前证书

```text
/etc/nginx/ssl/llmroute.club.pem
/etc/nginx/ssl/llmroute.club.key
```

私钥权限必须是 600。证书为 Cloudflare Origin CA,有效期核验:

```bash
chmod 600 /etc/nginx/ssl/llmroute.club.key
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -noout -subject -issuer -dates -ext subjectAltName
```

证书和私钥匹配核验:

```bash
openssl x509 -in /etc/nginx/ssl/llmroute.club.pem -pubkey -noout \
  | openssl pkey -pubin -outform der | sha256sum
openssl pkey -in /etc/nginx/ssl/llmroute.club.key -pubout \
  | openssl pkey -pubin -outform der | sha256sum
```

两个 SHA-256 必须完全相同。

### 6.2 当前主站路由要求

Nginx 中 `llmroute.club` 和 `www.llmroute.club` 应共同反代 `127.0.0.1:3002`,HTTP 跳 HTTPS。
修改任何 Nginx 配置后统一执行:

```bash
nginx -t && systemctl reload nginx
```

Cloudflare DNS 的 apex 与 `www` 记录都应指向 `82.29.71.122` 并开启橙云。SSL/TLS 模式保持
**Full (strict)**,不要使用 Flexible。

### 6.3 `api.llmroute.club` 待办

该域名目前不能写成“已上线”。配置前必须先确定路径策略:

- `/v1/*` 是否先进入 Portal proxy,以保留 Gemini 图片转换、请求体守门、Codex clamp 等能力。
- new-api 后台和非 `/v1/*` 路径是否需要公网开放,以及如何限制管理端访问。
- Nginx upstream、超时、SSE buffering、Cloudflare DNS 和 Full strict TLS 是否完整。

未完成以上设计和真实 API smoke 前,不要简单把整个域名直接反代到 new-api。

## 7. new-api 运维

### 7.1 当前容器重建基线

new-api 当前不是 Compose 管理,重建命令基线如下。执行前必须确认 `/root/new-api.env` 和
`/opt/new-api/data` 已备份,并且 `new-api_new-api-net` 存在:

```bash
docker run -d \
  --name new-api \
  --restart always \
  --network new-api_new-api-net \
  --env-file /root/new-api.env \
  -p 172.17.0.1:3000:3000 \
  -v /opt/new-api/data:/data \
  calciumion/new-api:latest
```

不要在旧容器仍占名时直接运行。任何 stop/rm/rename 前先 `docker inspect` 保存当前镜像、环境文件、
端口、网络和挂载信息。日常只需:

```bash
docker restart new-api
docker logs --since=10m new-api
```

### 7.2 连通性检查

```bash
docker ps --filter name=new-api
docker inspect new-api --format '{{range $name, $conf := .NetworkSettings.Networks}}{{$name}}{{"\n"}}{{end}}'
ss -lntp | grep -E ':3000\b'
curl -sS http://172.17.0.1:3000/api/setup
```

端口应显示 `172.17.0.1:3000->3000/tcp`,网络应包含 `new-api_new-api-net`。

## 8. 备份、恢复与回滚

### 8.1 Portal PostgreSQL 恢复

恢复会写生产数据,必须先停止写流量并再次备份现状。基本命令参考:

```bash
gunzip -c /opt/backups/silkroadai-portal/portal-YYYYMMDD-HHMMSS.sql.gz \
  | docker exec -i silkroadai-portal-db psql -U portal silkroadai_portal_prod
```

正式恢复前要确认备份完整、目标库状态、是否需要清库以及 migration 兼容性,不能直接照抄执行。

### 8.2 代码回滚

首选做法是在 `dev` 创建 revert、跑完整测试、fast-forward 到 `prod`,再按标准流程部署。紧急情况下可在
服务器临时 checkout 已知正常 SHA 并重建,但必须记录 SHA,事后恢复到 `prod`:

```bash
git switch --detach <KNOWN_GOOD_SHA>
docker compose -f docker-compose.prod.yml build \
  --build-arg APP_URL=https://llmroute.club portal
docker compose -f docker-compose.prod.yml up -d portal
```

Prisma migration 是 forward-only。代码回滚不会自动回滚 schema;涉及不兼容 migration 时必须制定数据库
恢复方案,不要用 `git reset --hard` 或 `prisma migrate reset` 处理生产事故。

## 9. 常见故障

### Portal 内部正常,公网超时

依次检查:

```bash
curl -I http://127.0.0.1:3002/login
systemctl status nginx --no-pager
nginx -t
ss -lntp | grep -E ':(80|443)\b'
firewall-cmd --list-services
getent ahostsv4 llmroute.club
```

内部 200 而公网失败通常在 Nginx、云安全组、Cloudflare DNS 或 SSL 模式。

### Portal 连不上 new-api

```bash
curl -sS http://172.17.0.1:3000/api/setup
docker exec silkroadai-portal node -e \
  "fetch('http://host.docker.internal:3000/api/setup').then(r=>console.log(r.status)).catch(console.error)"
docker inspect new-api --format '{{json .HostConfig.PortBindings}}'
docker network inspect new-api_new-api-net >/dev/null
```

重点确认 new-api 绑定 `172.17.0.1:3000`,Portal compose 的 `extra_hosts` 和网络 `gw_priority` 未被删除。

### DNS 解析失败导致 `dnf` 不可用

服务器曾出现公网 IP 可达但域名无法解析。当前连接名通常是 `System eth0`,恢复基线:

```bash
CONN="$(nmcli -t -f NAME con show --active | head -n1)"
nmcli con mod "$CONN" ipv4.ignore-auto-dns yes ipv4.dns "1.1.1.1 8.8.8.8"
nmcli con mod "$CONN" ipv6.ignore-auto-dns yes
nmcli con up "$CONN"
getent hosts mirrors.almalinux.org
```

### SSH 偶发超时或被关闭

```bash
ssh -4 root@82.29.71.122
```

服务器已出现大量公网爆破尝试。长期方案是配置 SSH key、验证新会话后关闭密码登录、限制 root 登录并启用
fail2ban/云防火墙白名单。修改 sshd 前必须保留一个已登录会话,避免把自己锁在服务器外。
