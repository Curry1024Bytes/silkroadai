# Silk Road AI Portal — 部署与运维手册（llmroute.club 环境）

> 本文档归档 2026-06-15 完成的 llmroute.club 独立生产环境部署全过程。
> 面向运维 / 开发，读完能独立完成「线上部署、改配置、看日志、本地起服务」。
> 这是与旧 VPS（silkroadai.io）**平行的第二套独立环境**，全新 new-api、空数据库。

---

## 0. 一句话理解整个系统

这是一个**给 new-api 套客户层**的项目。两层分工：

- **new-api**（独立开源项目，不在本仓库）= 真正连各家大模型、做路由和计费的「发动机」。
- **portal**（本仓库）= 客户注册 / 登录 / 充值 / 拿 key / 对话的「方向盘」，背后全靠调 new-api 干活。

**portal 没有 new-api 就是空壳**：能注册登录，但客户一调模型就报错。所以部署顺序是硬性的：**先 new-api（含配渠道），再 portal**。

## 1. 线上架构总览（llmroute.club）

```
                      公网 https://
                          │
              ┌───────────▼────────────┐
              │   Cloudflare（橙云代理）  │  SSL 模式：Full
              └───────────┬────────────┘
                          │
              ┌───────────▼────────────┐
              │   nginx（宿主机系统服务）  │  + 通配符 Origin 证书 *.llmroute.club
              └──┬──────────────────┬───┘
       llmroute.club          api.llmroute.club
                 │                  │
        ┌────────▼───────┐  ┌───────▼────────┐
        │ portal :3002    │  │  new-api :3000 │  （客户 API 入口 + 后台）
        │ (本仓库)         │  │  (calciumion)  │
        └────────┬────────┘  └───────┬────────┘
                 │                   │
        ┌────────▼────────┐  ┌───────▼────────┐
        │ portal-postgres  │  │ new-api-mysql  │
        │ (PG16, compose)  │  │ (MySQL 8.0)    │
        └─────────────────┘  └────────────────┘
```

### 域名布局

| 域名 | 指向 | 用途 |
|---|---|---|
| `llmroute.club` | portal :3002 | 客户门户（注册/登录/充值/对话界面） |
| `api.llmroute.club` | new-api :3000 | 客户 API 入口 + new-api 后台 |

⚠️ **客户调模型的 base URL 是 `https://api.llmroute.club/v1`**（指向 new-api），不是 portal 域名。portal 只是管理界面。写客户文档时要讲清楚。

### 4 个容器

| 容器名 | 镜像 | 端口绑定 | 怎么起的 |
|---|---|---|---|
| `silkroadai-portal` | 本地 build | `127.0.0.1:3002` | docker compose（prod.yml） |
| `silkroadai-portal-db` | postgres:16-alpine | 仅内部 5432 | docker compose（prod.yml） |
| `new-api` | calciumion/new-api:latest | `127.0.0.1:3000` | 手动 `docker run` |
| `new-api-mysql` | mysql:8.0 | 仅内部 3306 | 手动 `docker run` |

> 端口都绑 `127.0.0.1`（只本机可达），公网流量只能走 nginx → 更安全。

### 服务器信息

- **系统**：Rocky Linux 9.7（RHEL 9 系，用 `dnf`）
- **portal 项目目录**：`/opt/silkroadai-portal`
- **new-api 数据目录**：`/opt/new-api/data`
- **nginx 配置目录**：`/etc/nginx/conf.d/`
- **SSL 证书**：`/etc/nginx/ssl/llmroute.club.{pem,key}`（通配符 `*.llmroute.club`）

## 2. 配置文件机制（重要 — 与 Java 不同）

### 两份模板 + 一个真配置

| 文件 | 进 git？ | 作用 |
|---|---|---|
| `.env.local.example` | ✅ | 本地开发模板（localhost 那套），无密钥，给人 `cp` |
| `.env.prod.example` | ✅ | 线上模板（容器名+域名那套），无密钥，给人 `cp` |
| `.env` | ❌ 永不 | 真正生效的配置，填好密钥。Compose 和 node 进程读它 |

**用法**：
```bash
# 本地开发机
cp .env.local.example .env   # 填值

# 线上服务器
cp .env.prod.example .env    # 填值
chmod 600 .env               # 含密钥，锁权限
```

> Docker Compose **只认名字叫 `.env` 的文件**，不会读 `.example`。`.example` 只是模板。
> "选哪套环境" = "在哪台机器把哪个 example 拷成了 `.env`"，不是 compose 文件去挑 example。

### ⚠️ 构建时变量 vs 运行时变量（Java 没有的坑）

| 类型 | 例子 | 改了怎么生效 |
|---|---|---|
| **构建时**（`NEXT_PUBLIC_` 开头，本项目只有 `NEXT_PUBLIC_APP_URL`） | `NEXT_PUBLIC_APP_URL` | **必须重新 `docker compose up -d --build`**，只重启无效（值被编译进静态产物了） |
| **运行时**（其余全部） | `DATABASE_URL` / `NEWAPI_*` / `PORTAL_JWT_SECRET` / SMTP / OAuth… | 改完**重启容器**即可，不用 build |

### 必填项（缺了 portal 起不来）

| 配置项 | 填什么 |
|---|---|
| `DATABASE_URL` | `postgresql://portal:<DB密码>@portal-postgres:5432/silkroadai_portal_prod`（host 必须是容器名 `portal-postgres`） |
| `POSTGRES_PASSWORD` | 同上那个 DB 密码，**必须与 DATABASE_URL 里的完全一致** |
| `NEWAPI_BASE_URL` | `http://host.docker.internal:3000`（见 §4 网络坑） |
| `NEWAPI_ADMIN_TOKEN` | new-api 后台「个人设置 → 系统访问令牌」生成（⚠️ 见 §6 gotcha） |
| `NEWAPI_ADMIN_USER_ID` | `1`（new-api root 用户 id） |
| `PORTAL_JWT_SECRET` | `openssl rand -hex 32` 生成 |
| `ADMIN_TOKEN` | `openssl rand -hex 32` 生成 |
| `PORTAL_OSS_ENC_KEY` | `openssl rand -hex 32` 生成（⚠️ 投产后不可换） |
| `APP_URL` | `https://llmroute.club` |
| `NEXT_PUBLIC_APP_URL` | `https://llmroute.club` |

> 可选项（SMTP / 易支付 / OAuth / R2 / Tavily）先留占位，核心链路通了再逐个开。

## 3. 从零部署全过程（线上）

### 3.1 服务器准备

```bash
# 1. 装 nginx
dnf install -y nginx
systemctl enable --now nginx

# 2. 开防火墙 80/443（如果用 firewalld）
firewall-cmd --permanent --add-service=http
firewall-cmd --permanent --add-service=https
firewall-cmd --reload
# ⚠️ 云厂商控制台的安全组也要放行 80/443

# 3. 装 Docker + Compose
dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
dnf install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
systemctl enable --now docker
docker --version && docker compose version
```

### 3.2 nginx + SSL

证书来自 Cloudflare Origin 证书（通配符 `*.llmroute.club`），放在 `/etc/nginx/ssl/`。
Cloudflare SSL 模式设为 **Full**。DNS 在 Cloudflare 加 A 记录（橙云代理）指向服务器 IP。

两个站点配置文件在 `/etc/nginx/conf.d/`：
- `llmroute.club.conf` → 反代 portal（见 §3.5）
- `api.llmroute.club.conf` → 反代 new-api（见 §3.3）

改完配置统一执行：
```bash
nginx -t && systemctl reload nginx
```

### 3.3 部署 new-api（先做，发动机）

```bash
# 1. 建专用网络
docker network create new-api-net

# 2. 起 MySQL 8.0（密码自己生成，存好）
docker run -d --name new-api-mysql --restart always \
  --network new-api-net \
  -e MYSQL_ROOT_PASSWORD=<你的MYSQL密码> \
  -e MYSQL_DATABASE=new_api \
  -v /opt/new-api/mysql:/var/lib/mysql \
  mysql:8.0

# 3. 起 new-api（3 个密钥替换成自己存好的值）
mkdir -p /opt/new-api/data
docker run -d --name new-api --restart always \
  --network new-api-net \
  -p 127.0.0.1:3000:3000 \
  -e SQL_DSN="root:<MYSQL密码>@tcp(new-api-mysql:3306)/new_api" \
  -e TZ=Asia/Shanghai \
  -e SESSION_SECRET=<openssl rand -hex 32> \
  -e CRYPTO_SECRET=<openssl rand -hex 32> \
  -v /opt/new-api/data:/data \
  calciumion/new-api:latest
```

new-api 的 nginx 配置 `/etc/nginx/conf.d/api.llmroute.club.conf`：
```nginx
server {
    listen 80;
    server_name api.llmroute.club;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl http2;
    server_name api.llmroute.club;
    ssl_certificate /etc/nginx/ssl/llmroute.club.pem;
    ssl_certificate_key /etc/nginx/ssl/llmroute.club.key;
    client_max_body_size 100m;
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
```

⚠️ **部署后第一件事**：浏览器开 `https://api.llmroute.club`，用默认 `root / 123456` 登录后**立刻改强密码**（公网暴露的后台，慢一步就可能被爆破盗用上游 key）。

### 3.4 部署 portal（后做，方向盘）

```bash
# 1. 拉代码（仓库 fork：github.com/Curry1024Bytes/silkroadai）
mkdir -p /opt/silkroadai-portal && cd /opt/silkroadai-portal
git clone https://github.com/Curry1024Bytes/silkroadai.git .

# 2. 准备 .env
cp .env.prod.example .env
chmod 600 .env

# 3. 构建并启动（首次 --build 编译 3-8 分钟，CPU 会满，正常）
docker compose -f docker-compose.prod.yml up -d --build
```

### 3.5 接通 portal ↔ new-api（关键，见 §4 网络坑）

```bash
# 确认 .env 里 NEWAPI_BASE_URL="http://host.docker.internal:3000"
docker compose -f docker-compose.prod.yml up -d portal   # 重启生效
```

portal 的 nginx 配置 `/etc/nginx/conf.d/llmroute.club.conf`（与 §3.3 同结构，
`server_name llmroute.club www.llmroute.club`，`proxy_pass http://127.0.0.1:3002`）。

## 4. ⚠️ 核心坑：portal 连不上 new-api（ECONNREFUSED）

部署当天踩到的最大坑，记牢。

**症状**：portal 日志报
```
[shadow-meter] scan failed: connect ECONNREFUSED 172.17.0.1:3000
```

**原因**：
- new-api 绑的是 `127.0.0.1:3000`（只本机回环，为安全）
- portal 容器通过 `host.docker.internal` 去连，解析成 docker 网桥网关 `172.17.0.1`
- 宿主机的 `127.0.0.1` 和 `172.17.0.1` 是**两个不同的网络接口**，new-api 没在 `172.17.0.1` 上监听 → 连接被拒

**解法（让 portal 走宿主机 3000 端口）**：
```bash
# .env 里保持 NEWAPI_BASE_URL="http://host.docker.internal:3000"
docker compose -f docker-compose.prod.yml up -d portal
```

**验证连通**：
```bash
docker exec silkroadai-portal sh -c "wget -qO- --timeout=5 http://host.docker.internal:3000/api/status | head -c 100"
# 返回 JSON 即通
```

⚠️ 如果这个验证失败，优先检查宿主机上的 new-api 是否真的在 `127.0.0.1:3000` 监听，
以及 `docker-compose.prod.yml` 里 portal 的 `extra_hosts` / `gw_priority` 是否还在。

### 上线前支付检查（易支付 / zpayz）

生产支付当前走易支付 `easypay`,网关为 zpayz。上线前必须核对 VPS 真实配置 `/opt/silkroadai-portal/.env`:

```env
PAYMENT_PROVIDERS=easypay
ENABLED_PAYMENT_TYPES=alipay,wxpay
EASY_PAY_PID="2026072211025295"
EASY_PAY_PKEY="<从 zpayz 商户后台复制,不要提交到 git>"
EASY_PAY_API_BASE="https://zpayz.cn"
EASY_PAY_NOTIFY_URL="https://llmroute.club/api/easy-pay/notify"
EASY_PAY_RETURN_URL="https://llmroute.club/pay/result"
PRODUCT_NAME="LLmRoute 余额充值"
```

注意:`EASY_PAY_API_BASE` 不要带末尾 `/`,代码会自动拼 `/mapi.php` 和 `/api.php`。zpayz 商户后台的异步通知地址必须填 `https://llmroute.club/api/easy-pay/notify`,同步跳转地址必须填 `https://llmroute.club/pay/result`。

zpayz 接口对应关系:

- 本项目创建支付走 **API接口支付**:`POST https://zpayz.cn/mapi.php`,不是页面跳转支付 `/submit.php`。
- 发起支付时代码会传:`pid` / `type` / `out_trade_no` / `notify_url` / `return_url` / `name` / `money` / `clientip` / `sign` / `sign_type`,以及可选 `cid` / `device`。
- zpayz 成功返回的 `payurl` / `qrcode` / `img` 都已兼容;前端优先展示 `img`/`qrcode` 二维码。
- 支付结果通知是 `GET notify_url?...`,本项目 `/api/easy-pay/notify` 只处理 GET,验签成功后返回纯字符串 `success`;重复通知走订单状态机幂等处理。
- zpayz 文档的订单查询示例是 GET 且 URL 带 `key`;代码当前为避免密钥进 URL 日志,用 POST 调 `/api.php` 查询。该查询不是入账主路径,上线 smoke 若发现平台查询不兼容再改成 zpayz 要求的 GET。

支付上线 smoke:

1. 登录真实测试账号,打开 `https://llmroute.club/pay`。
2. 发起最小金额 `¥10` 充值,选择支付宝或微信。
3. 确认跳到 zpayz/二维码页,支付完成后回到 `/pay/result`。
4. 查看 `/balance`,确认余额增加;同时看日志中没有 `[easy-pay/notify] signature verification failed`。

## 6. new-api 必知 gotcha（CLAUDE.md 摘录）

| # | 坑 | 要点 |
|---|---|---|
| #13 | `GET /api/user/token` 是 **rotate 不是 read** | 后台「系统访问令牌」生成按钮**点一次就让旧的失效**。生成后立刻存好别再点。`NEWAPI_ADMIN_TOKEN` 人工管理，丢了只能后台 UI 重新生成→写回 .env→重启 |
| #14 | 一个上游多种格式 → 配多个渠道 | 一个渠道只能一种协议类型。同上游若同时支持 OpenAI 和 Claude 格式，要配两个渠道（同 base+key，类型不同，各列模型） |
| #15 | 渠道改动后短名可能失效 | 改渠道 / 上游扩容后，W1 时代短名（如 `deepseek-v4-flash`）可能 503。短名必须同时出现在 `channel.models` 字段里。修复脚本：`pnpm tsx scripts/rebuild-channel-model-mapping.ts <channel_id> --apply` |
| #12 | token 必须 `unlimited_quota=true` | portal 创建的 token 永远 unlimited；预算关由 `user.quota` 单点控制（充值走 add_quota 给 user） |
| #20 | 时间显示要带时区 | server 端 `toLocaleString` 必须显式 `{ timeZone: 'Asia/Shanghai' }`，否则容器默认 UTC 显示错 |

完整 gotcha 列表见仓库根 `CLAUDE.md`。

## 7. 本地开发怎么起

```bash
# 1. 装依赖

# 2. 配置
```

## 10. portal 管理后台登录

⚠️ 别和 **new-api 后台**（`https://api.llmroute.club`，默认 `root/123456`）搞混 —— 那是另一套独立系统的后台。本节说的是 **portal 自己的管理后台**。

### 登录地址

```
https://llmroute.club/admin/login
```

只有邮箱 + 密码，**没有注册 / OAuth 入口**。admin 与客户共用同一套登录（同一个 `silkroad_session` cookie），登录成功跳 `/admin`，角色检查在服务端做。admin 账号**不能自助注册**，必须先注册成普通客户，再用脚本赋权升级。

### 首次开通管理员（3 步）

**1. 先注册一个普通客户账号**

到 `https://llmroute.club/register` 用你的邮箱注册一个普通账号（admin 只能从已注册客户「升级」）。

**2. 给这个邮箱赋予管理员角色**

SSH 到服务器，在 portal 容器里跑赋权脚本：

```bash
docker exec -it silkroadai-portal pnpm tsx scripts/grant-admin.ts <你的邮箱> superadmin
```

> 若容器内 `pnpm tsx` 不可用（生产镜像可能精简了 devDeps），可改为直连 PG 用 SQL 改：
> ```bash
> docker exec -it silkroadai-portal-db psql -U portal silkroadai_portal_prod \
>   -c "UPDATE users SET role='superadmin' WHERE email='<你的邮箱>';"
> ```

**3. 登录后台**

回到 `https://llmroute.club/admin/login`，用刚注册的邮箱密码登录。

### 角色说明（`scripts/grant-admin.ts`）

| role | 含义 |
|---|---|
| `superadmin` | 平台超管，权限最全（租户管理 `/admin/tenants` 专属）。**给自己就用这个** |
| `admin` | 平台管理员 OR 白标 partner 运营（tenantScope 限制只看自己租户） |
| `staff` | ⚠️ 后台入口门槛是 role ≥ admin，**staff 进不了后台 UI**（会被重定向回登录）。枚举值保留供将来细分 |
| `customer` | 降级 / 撤销后台权限 |

> 脚本走 `.env` 的 `DATABASE_URL`，只改 portal 自有 `users` 表的 `role` 字段，**不碰 new-api、不动 tenant_id**，安全可重复执行。

## 11. 用 Navicat 连线上数据库（SSH 隧道）

线上 portal 数据库是 **PostgreSQL**（不是 MySQL），Navicat 要新建 **PostgreSQL** 连接。

### 前提：PG 容器已绑回环端口

`docker-compose.prod.yml` 的 `portal-postgres` 服务发布了 `127.0.0.1:5432:5432`（**只绑回环，不暴露公网** —— 公网流量没有路径到这个端口，只有 SSH 进服务器或走隧道的人能连）。确认：

```bash
docker ps --format '{{.Names}}: {{.Ports}}' | grep portal-db
# 期望：silkroadai-portal-db: 127.0.0.1:5432->5432/tcp
```

> 改动来源：2026-06-24 给 `portal-postgres` 加了回环端口发布，方便运维用 Navicat 走 SSH 隧道连库。**绝不能改成 `0.0.0.0:5432` 或公网直连**，那会把 Postgres 裸暴露到公网被爆破。

### Navicat 配置

新建 PostgreSQL 连接，**两个标签页都要填**：

**「常规」标签页**

| 字段 | 值 | 说明 |
|---|---|---|
| 主机 | `127.0.0.1` | ⚠️ **必须是 127.0.0.1，不是服务器公网 IP** |
| 端口 | `5432` | |
| 初始数据库 | `silkroadai_portal_prod` | |
| 用户名 | `portal` | |
| 密码 | 服务器 `.env` 的 `POSTGRES_PASSWORD` | `grep POSTGRES_PASSWORD /opt/silkroadai-portal/.env` |

**「SSH」标签页** — 勾「使用 SSH 通道」

| 字段 | 值 |
|---|---|
| 主机 | 服务器公网 IP |
| 端口 | `22` |
| 用户名 | `root`（或你的 SSH 用户） |
| 验证方法 | 密码（填 SSH 登录密码，**不是数据库密码**） |

**「SSL」标签页**：确认「使用 SSL」**不勾**（PG 没配 SSL，勾了会握手失败报错）。

### ⚠️ 最容易踩的坑：「常规」页主机要填 127.0.0.1

Navicat SSH 隧道的逻辑：**先 SSH 进服务器，再从「服务器视角」去连「常规」页填的地址**。所以隧道场景下「常规」页主机必须是 `127.0.0.1`（= 服务器自己的回环 5432，正好命中映射端口）。

填成服务器公网 IP 会怎样：隧道进服务器后又拿公网 IP 绕回去连公网 5432（没开），表现为隧道那段是绿的、但「SSH服务器 → 数据库」这段红，报错：

```
server closed the connection unexpectedly
This probably means the server terminated abnormally
before or while processing the request.
```

**改回 `127.0.0.1` 即可连通。**（2026-06-24 实战定位）

### 排查顺序（连不上时）

```bash
# 1. 端口映射在不在
docker ps --format '{{.Names}}: {{.Ports}}' | grep portal-db   # 要有 127.0.0.1:5432->5432/tcp

# 2. 容器内直连（绕过映射端口，验证库本身健康）
docker exec -it silkroadai-portal-db psql -U portal silkroadai_portal_prod -c "select 1;"

# 3. 从宿主机回环连（模拟 Navicat 隧道走的路径）
docker run --rm --network host -e PGPASSWORD='<密码>' postgres:16-alpine \
  psql "postgresql://portal@127.0.0.1:5432/silkroadai_portal_prod" -c "select 1;"
```

1、2、3 都通 → 问题必在 Navicat 侧：①「常规」页主机是否误填公网 IP（应为 127.0.0.1）②「SSL」是否误勾。

> FinalShell 等客户端也可自建本地端口转发（local forward：本地 15432 → 服务器 127.0.0.1:5432）替代 Navicat 内置隧道，然后 Navicat 关 SSH 隧道直连 `127.0.0.1:15432`。

## 12. 本地开发连「测试服务器」工作流（换设备即开即用）

> 适用场景：家里 / 公司多台电脑，都用同一台阿里云测试服务器的 new-api + Postgres，
> 本地只跑 `pnpm dev`（热重载快）。数据库和 new-api 不在本机，走 SSH 隧道连过去。
> 这样换设备只需「装环境 → clone → 配 .env → 起隧道 → pnpm dev」五步，数据共享。

### 12.1 测试服务器信息

- **服务器**：阿里云，`root@114.55.85.41`（SSH 公钥登录，见 §12.3）
- **两个容器**（都绑 `127.0.0.1`，只回环，**必须走 SSH 隧道才能从本机连**）：

| 容器名 | 镜像 | 端口绑定 | 用途 |
|---|---|---|---|
| `portal-dev-newapi` | calciumion/new-api:latest | `127.0.0.1:3000` | 模型路由 / 计费后端 |
| `portal-dev-pg` | postgres:16-alpine | `127.0.0.1:5433`（→容器内 5432） | portal 数据库 |

- **数据库凭据**：用户 `portal` / 密码 `devpass123` / 库 `silkroadai_portal_dev`

> ⚠️ 这两个容器跟 `docker-compose.dev.yml`（本机起库）是**二选一**：用测试服务器这套，本机就别再起本地 PG / new-api，否则端口撞（隧道会报 `Address already in use`）。

### 12.2 阿里云安全组端口

new-api（3000）和 PG（5433）在服务器上都绑 `127.0.0.1`，**只通过 SSH 隧道访问，不直接暴露公网**，所以安全组**只需放行 22（SSH）**。

⚠️ **不要**在安全组放行 3000 / 5433 到 `0.0.0.0` —— 那会把 new-api 后台和数据库裸暴露公网被爆破。回环绑定 + SSH 隧道是当前的安全模型，保持现状。

### 12.3 首次配 SSH 免密（每台新设备做一次）

```bash
# 1. 本地生成密钥（已有 ~/.ssh/id_ed25519 可跳过），一路回车
ssh-keygen -t ed25519

# 2. 把公钥装到服务器（这一步要输一次 root 密码;
#    Windows 终端密码粘不上是正常的，用【右键粘贴】或手敲，输入不回显）
type %USERPROFILE%\.ssh\id_ed25519.pub | ssh root@114.55.85.41 "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
```

之后 `ssh root@114.55.85.41` 不再要密码，隧道命令直接通。

### 12.4 起 SSH 隧道（每次开发前）

```bash
ssh -fN -L 3000:localhost:3000 -L 5433:localhost:5433 -o ServerAliveInterval=60 root@114.55.85.41
```

- `-f` 后台运行，`-N` 不开 shell → **成功后没有任何输出，直接回到命令行就是对的**。
- 把服务器的 3000 / 5433 转发到本机同名端口，本地代码当作 `localhost:3000` / `localhost:5433` 用。
- 断网 / 重启电脑后隧道会断，要重跑这条。

**验证隧道通了**：

```bash
# Windows PowerShell
curl http://localhost:3000/api/status     # 返回 200 + JSON 即通

# 端口被隧道占上没
netstat -ano | findstr "3000 5433"
```

**常见报错**：
- `bind: Address already in use` / `cannot listen to port` = 该端口已被占（隧道已经在跑，或本机还开着本地 PG/new-api 容器）。先停掉本地容器或杀掉旧隧道再起。

### 12.5 本地 .env（连测试服务器版）

`cp .env.local.example .env`，关键三行确认成下面这样（其余密钥用 `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` 各生成一个填进去，**别把真值写进 git**）：

```bash
DATABASE_URL="postgresql://portal:devpass123@localhost:5433/silkroadai_portal_dev"
NEWAPI_BASE_URL="http://localhost:3000"
NEWAPI_ADMIN_TOKEN="<在 http://localhost:3000 后台→个人设置→系统访问令牌 生成，gotcha #13 点一次别再点>"

# 这三个本地随机生成即可（换设备可复用同一份 .env，不必每台重生成）：
PORTAL_JWT_SECRET="<openssl rand -hex 32>"
ADMIN_TOKEN="<openssl rand -hex 32>"
PORTAL_OSS_ENC_KEY="<openssl rand -hex 32>"
```

> `.env` 不进 git。换设备最省事的做法：把这份 `.env` 存到 1Password / 私密笔记，新机器直接拷过去。
