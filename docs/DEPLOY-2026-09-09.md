## 验收脚本修正及仍存在的限制

第一轮脚本失败没有被隐藏：原脚本和日志保存在本机证据目录，随后只修正了脚本的协议判断与 HTTP 客户端，没有改产品代码、上游回归测试或 Cloudflare 配置。

1. Gemini 预检透传 new-api 的 `Access-Control-Allow-Headers: *`；原脚本错误要求逐字列出 `x-goog-api-key,content-type`。无 Cookie、`credentials=omit` 的请求允许这些头通过通配符，`Authorization` 仍必须显式允许；这是本次复核范围。依据 [WHATWG Fetch 的 CORS 语义](https://fetch.spec.whatwg.org/#http-new-header-syntax) 和 [Authorization 的非通配规则](https://fetch.spec.whatwg.org/#cors-non-wildcard-request-header-name) 修正判断。`v1beta` 产品代码与回滚版本逐字一致；没有将浏览器 Cookie 凭据模式或 Gemini Bearer 跨域场景报为已验收。
2. 公网对默认 `Python-urllib/3.9` 返回 Cloudflare 403/1010；同一假 Key 请求改用标准 curl 得到正常 401，真实 Key 用 curl 得到 200。此项客户端兼容限制仍存在，没有关闭防护或新增绕过规则。[Cloudflare 对 1010 的说明](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/) 将其归因于客户端浏览器签名拦截。后续若需支持该默认客户端，应单独审查 API 域名的相应策略，不能把本次部署记为已修复。
