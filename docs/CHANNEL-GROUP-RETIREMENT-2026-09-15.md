# Portal 分组一键清理（2026-09-15）

本轮解决「已在 new-api 删除分组，回到 Portal 却还需逐个编辑模型 JSON 才能删除」的问题。现在从渠道分组列表点击「删除」，在同一个对话框核对影响并确认，即可一起清理 Portal 分组与该档次的模型关联。

当前状态：开发、完整测试、隔离 PostgreSQL、生产构建及本地浏览器验收已完成；上线验收待本报告末尾补记。本报告当前不表示功能已经发布，也不表示已删除任何生产分组。

## 管理员操作

1. 在「渠道分组」找到要清理的分组，点击「删除」。
2. 对话框自动读取当前状态，展示将清理的模型关联、将下架的模型、已有 Key 数量，以及 new-api 分组核对结果。
3. 如果删除的是默认档次，在同一对话框选择接任的默认档。只有一个合法候选时自动选中；没有合法候选时显示原因并阻止确认。
4. 核对后确认删除。成功提示会列出清理了多少模型关联、下架了多少模型，以及新的默认档次（如有）。

无需先到模型管理逐个修改 JSON。确认时如果配置已经变化或预览过期，页面会重新读取影响；管理员须核对新预览后再次确认，不会自动重试删除。

## 删除范围和客户影响

| 对象                                                            | 本次行为                             |
| --------------------------------------------------------------- | ------------------------------------ |
| 选中的 Portal 分组                                              | 删除该记录，新建 Key 不再提供此档次  |
| 本租户模型的目标档次映射                                        | 一起移除，包含已停用模型中的旧关联   |
| 同一模型的其他档次映射                                          | 原样保留，包含原有扩展字段           |
| 移除后完全没有其他映射的启用模型                                | 自动下架，保留模型实体               |
| 原本已停用的模型                                                | 清理目标映射后保持停用，不会自动启用 |
| 其他租户的同名分组、模型与 Key                                  | 不修改                               |
| 目录价格、价格历史、成本规则及成本版本                          | 保留，不因清理分组而级联删除         |
| 已有客户 Key、用量和历史记录                                    | 保留，不删除、不迁移、不撤销         |
| 客户 `allowed_tier_keys` 白名单与 `UserTierMultiplier` 倍率记录 | 保留，不自动清空或改写               |
| new-api 的分组、渠道、模型、价格和 Key                          | 全部不修改                           |

这里的「自动下架」仅指清除目标映射后没有任何其他档次关联的模型。如果还剩其他无效、停用或归属错误的映射，系统明确指出问题并阻止操作，不顺带修复或删除其他档次配置。

删除 Portal 分组会使本档目录和新建 Key 的选档入口消失。已有 Key 的真实可用性仍由 new-api 决定，保留 Key 不代表它仍能正常调用。仅获准使用此档的客户，需要管理员另行分配可用档次；系统不会把最后一项白名单清成空数组，以免把有限授权意外变成不受限制。已有客户倍率记录也不会被静默移除。

## new-api 核对结果

核对只发 GET 请求，使用完整分页渠道列表和白名单选项 `UserUsableGroups`、`GroupRatio`。不会仅根据前 100 条渠道或过滤后的可见分组判断删除；`@` 隐藏标签和零倍率仍视为存在，合法空字典 `{}` 则是有效读取结果。

| 状态      | 含义与处理                                                                                                                         |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `missing` | 完整渠道列表没有该分组引用，两个分组字典也都明确不含该名称。提示可以清理 Portal 中的对应记录；这不等于所有旧登记渠道 ID 都已删除。 |
| `present` | 任一完整来源仍明确包含该分组。提示 new-api 配置仍存在，但允许管理员确认只清理 Portal。                                             |
| `unknown` | 读取失败、响应不完整或格式不合法，无法完整确认。明确说明无法核实，仍允许管理员确认只清理 Portal，不会冒充「上游已删除」。          |

上游状态是影响提示，不是强制要求管理员先在 new-api 删除的开关。本功能始终只清理 Portal。渠道对象中的密钥和其他敏感字段不进入预览响应或签名快照；只保留核对分组所需的非敏感成员关系。

## 实现与一致性保护

- 页面改用 `POST /api/admin/channel-groups/[id]/retire`，区分 `action=preview` 与 `action=apply`。原有 DELETE 接口和其保护性拒绝行为保留，兼容旧调用方。
- 路由先验证 superadmin 并定位选中分组，再以其真实 `tenant_id` 查询模型、默认候选及通过用户关系关联的 Key。不会凭同名 tier 跨租户清理。
- 预览不修改数据库。它对目标分组、同租户分组和模型、相关 Key 的身份及状态、默认替代选择和上游核对证据生成 HMAC 签名，并绑定操作者身份、角色、租户与 break-glass 身份。
- 签名使用既有 `PORTAL_JWT_SECRET`，有效期为十分钟。快照日期先转换为 ISO 字符串，确保仅 `updated_at` 改变也会使旧预览失效。Key 绑定身份与状态而非仅数量，且不会读取完整令牌值。
- 提交前重新读取上游状态。来源记录携带核对时的分组名称，必须与重新读取的 Portal 分组名称一致，防止在读取期间改名后展示旧名称的核对结果。
- 本地修改放在同一个 Serializable 事务内，先取得既有价格发布协调锁，再重新构建计划并验证签名。有活动价格发布任务时拒绝清理。事务中不发网络请求。
- 模型更新、分组删除和必要的默认档替换一起提交或回滚。替代默认时先删除旧默认，再设置新默认，遵守 PostgreSQL 立即生效的默认档唯一索引。
- 最终配置必须保留有效默认档和合法启用拓扑。更新和删除条件带租户及 `updated_at`；并发修改、过期或冲突要求重新预览。已成功的删除无法再次重放。
- 前端取消旧的预览请求，旧响应不能覆盖新的默认选择；执行期间禁止重复确认。错误消息不回显 new-api 原始响应、密钥或数据库内部错误。

本轮没有数据库 migration，没有新增环境变量、依赖、Docker、Nginx 或 Cloudflare 配置。new-api 源码与配置均未修改。
