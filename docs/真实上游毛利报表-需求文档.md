# 真实上游毛利报表

> 状态：进行中（需求已梳理，暂不实现）
>
> 日期：2026-08-10。本文只定义后续开发口径，不改变当前计费、充值、余额或 new-api 配置。

## 1. 目标

为 LLmRoute Portal 增加一个只读的真实 API 毛利报表，回答三个问题：

1. 指定时间范围内，客户实际消费了多少人民币；
2. 同一批调用在上游实际花了多少人民币；
3. 两者相减后的 API 毛利和毛利率是多少。

报表必须支持按天、周、月查看，并可按客户账号、销售分组、模型和上游线路下钻。

本功能是运营/财务对账工具，不是新的计费链路。它不得改变客户余额、new-api quota、充值到账或请求路由。

## 2. 已确认的计费事实

### 2.1 当前我方计费口径

- new-api 是当前客户的实际计费事实源，Portal 的 BILLING_SOURCE 仍为 newapi；不得为了让报表有数据而切换到 Portal 账本。
- new-api QuotaPerUnit=500000，Portal NEWAPI_QUOTA_PER_USD=500000，两边一致。
- Portal USD_TO_CNY_RATE=7.2。
- 我方收入应从 new-api 成功消费日志的 raw quota 计算，不使用页面四舍五入后的金额：

```text
retail_cny = SUM(newapi_quota) / 500000 × 7.2
```

- 失败请求、没有实际扣 quota 的请求不计入收入；退款日志应从对应时间范围的净消费中扣除。

### 2.2 当前线路规则

| 我方分组 | 我方销售倍率 | 上游规则     |              真实成本口径 | 状态   |
| -------- | -----------: | ------------ | ------------------------: | ------ |
| GPT 特惠 |         0.12 | 上游 1x      | ¥1 = $10，即成本倍率 0.10 | 已接入 |
| GPT Pro  |         0.20 | 上游号池规则 |       已确认成本倍率 0.13 | 已接入 |
| CCMax    |         暂无 | 尚未接入     |                      暂无 | 排除   |

成本规则必须按线路保存，而不是把我方 GroupRatio 当成采购成本。充值比例目前固定，但每一笔成本记录仍须保存当时的比例快照，以免未来上游改价后重算历史。

### 2.3 已核验的同请求样例

同一条 gpt-5.6-sol 请求：输入 18,458、输出 231、缓存读取 13,056。

上游按官方 1x 显示 $0.040468：

```text
上游成本 = $0.040468 / 10 = ¥0.0040468
我方售价 ≈ $0.040468 × 0.12 × 7.2 = ¥0.034964
毛利 ≈ ¥0.034964 - ¥0.0040468 = ¥0.030917
毛利率 ≈ 88.4%
```

报表必须使用底层精确值，不能使用 Portal 页面显示的 ¥0.03 作为计算输入。

## 3. 与现有“影子计量”报表的关系

当前 /admin/billing-shadow 是 P4a/P4b 观察报表，不是本需求的真实毛利报表：

- UsageRecord.newapi_quota 已保存 new-api raw quota，但现有毛利聚合刻意不使用它；
- UsageRecord.cost_cny 是 Portal 目录价计算出的零售价，不是上游真实成本；
- 成本来自 CatalogPrice.cost_cny_per_1m 的单一每百万 Token 字段，不区分输入、输出、缓存；
- 它要求 Portal meter 的 matched 记录才能计入零售，所以当前 BILLING_SOURCE=newapi 时可以出现“有调用、零售 ¥0”；
- 页面是只读的，不对任何客户余额生效。

后续真实毛利报表可以复用页面布局和权限守门，但不得把现有目录估算继续称为真实上游成本。旧页面保留作为兼容/观察入口，或在新报表上线后明确标记为“目录估算版”。

## 4. 业务口径

### 4.1 收入

收入是客户实际使用 API 消耗的金额，不是充值流水金额。充值、赠送额度、退款和余额属于现金流/账务维度，不能直接当作本期 API 销售额。

按 new-api 日志计算时：

- 只纳入成功消费日志；
- 按 quota 原始值计算；
- 对退款做净额处理；
- 保留原始 quota、换算参数和换算后的 CNY，便于复核。

### 4.2 成本

成本优先使用上游同一请求的实际扣费记录：

```text
cost_cny = upstream_charged_amount × effective_cny_per_upstream_unit
```

对于 GPT 特惠：

```text
cost_cny = upstream_fee_usd / 10
```

无法取得上游逐请求实扣时，才允许使用“官方 1x Token 价格 × 线路成本倍率”的估算值。估算记录必须标记 estimated，不能和 verified 实际成本混在一起后仍显示为已核验毛利。

### 4.3 毛利与毛利率

```text
gross_profit_cny = retail_cny - cost_cny
gross_margin_rate = gross_profit_cny / retail_cny
```

必须先汇总收入和成本再计算毛利率，不能平均每条调用的毛利率。

API 毛利不包含支付手续费、服务器、人工、税费等固定或运营成本。以后如需净利润，应另设费用台账，不能修改 API 毛利口径。

## 5. 筛选与展示需求

### 5.1 时间筛选

- 预设：今天、昨天、近 7 天、本周、本月、上月；
- 支持自定义开始/结束日期；
- 查询时间统一以北京时间（Asia/Shanghai）解释，数据库仍可用 UTC 存储；
- 自定义区间使用“开始包含、结束不包含”，避免跨天重复；
- 支持按天、按周、按月聚合；周边界固定为北京时间周一 00:00。

### 5.2 业务筛选

- 客户账号：按邮箱搜索，内部使用 Portal user_id 过滤；
- 我方分组：GPT 特惠、GPT Pro；
- 模型：如 gpt-5.6-sol；
- 上游线路/渠道：用于区分不同采购规则；
- 数据状态：全部、已核验成本、估算成本、未匹配。

客户筛选默认可选“全部客户”。管理员自己的测试 Key 可以单独标记并支持排除，但不能静默从总账中删除。

### 5.3 汇总卡与明细

在所有筛选条件下显示：

- 调用次数；
- 客户消费（零售）¥；
- 上游成本 ¥；
- API 毛利 ¥；
- 毛利率；
- 已核验成本覆盖率；
- 未匹配/仅估算调用数。

至少提供四种明细视图：

1. 按日期（天/周/月）汇总；
2. 按模型 × 我方分组；
3. 按客户账号；
4. 按上游线路。

每行显示调用数、Token（输入/输出/缓存如可取得）、我方售价、上游成本、毛利、毛利率、核验状态。点击行可下钻到请求级对账明细。

毛利率必须同时显示成本覆盖率。覆盖率不足 100% 时，不能把未录成本的调用当作零成本，否则会虚高。

## 6. 数据契约与关联要求

### 6.1 我方消费记录

优先复用已有 UsageRecord 的：

- newapi_log_id；
- user_id / newapi_user_id；
- model_slug、tier；
- input_tokens、output_tokens；
- newapi_quota；
- log_created_at。

需要补齐缓存 Token、请求 ID、渠道/线路等字段时，不能破坏现有 UsageRecord 以 newapi_log_id 为幂等锚点的约束。

### 6.2 上游成本记录

后续应新增独立的成本台账（具体表名在实现阶段确定），最少包含：

- 我方 newapi_log_id 或稳定 Request ID；
- 上游 Request ID（若上游提供）；
- 上游线路/渠道和上游模型；
- 上游原始计费金额及币种；
- 实际人民币成本；
- 当时的充值比例/成本倍率快照；
- verified / estimated / unmatched 状态；
- 来源（人工导入、上游 API、定时同步）；
- 原始证据的脱敏摘要和记录时间。

关联优先级：稳定 Request ID → 同一渠道的时间窗口 + 模型 + Token 明细 → 人工确认。无法可靠关联的记录必须进入未匹配清单，不能自动配对后算进正式毛利。

### 6.3 价格版本

销售倍率、上游成本倍率、充值比例和汇率都必须带生效时间。历史报表使用调用发生时的版本快照，不使用当前值回算历史。

## 7. 接口与权限建议

建议新增独立只读接口和页面：

```text
GET /api/admin/margin-report
/admin/margin-report
```

请求参数至少包含：start、end、bucket=day|week|month、user_id 或 email、tier、model、route、status。

权限沿用现有平台级 admin/superadmin 守门和 tenant scope。客户本人不能访问该报表；日志、Key、邮箱等敏感信息不能出现在公开 API。

## 8. 非目标与安全边界

- 不切换 BILLING_SOURCE；
- 不修改 User.billing_mode；
- 不向 new-api 写 quota、用户、Key 或计费配置；
- 不复制请求、不调用第二个上游、不增加上游成本；
- 不用 CatalogPrice.cost_cny_per_1m 冒充已核验上游账单；
- 不把充值金额、账户余额或 new-api 的销售 quota 当成采购成本；
- CCMax 未接入前不出现在正式毛利汇总中。

## 9. 验收标准

1. 用已核验的 gpt-5.6-sol 同请求样例，报表得到约 ¥0.03496 销售、¥0.00405 成本、¥0.03092 毛利和约 88.4% 毛利率；
2. 页面使用精确底层金额，不能用 ¥0.03 这种展示四舍五入值参与计算；
3. 按天、周、月切换时，北京时间边界正确，汇总与明细合计一致；
4. 按邮箱筛选只返回对应 Portal user_id 的记录；
5. GPT 特惠和 GPT Pro 使用各自的历史成本规则，不能把 .12/.20 当采购成本；
6. 未匹配、估算、退款、失败请求分别可见且不静默混入正式核验毛利；
7. 缺少上游成本时，页面显示“待核验/待补成本”，不能显示虚假的 100% 毛利；
8. 页面、接口、定时任务全程只读，不改变客户余额、new-api quota、充值或请求成功率；
9. 同一批数据按客户、模型、线路、时间不同维度汇总后，总额可相互对账；
10. 任何成本/汇率/倍率修改都保留历史版本，历史期间刷新结果不漂移。

## 10. 实施顺序（后续）

### P0：冻结口径

确认收入以 new-api raw quota 为当前唯一销售来源；确认上游日志能否提供逐请求实际美元扣费；冻结 GPT 特惠/GPT Pro 的规则版本。

### P1：成本台账

先支持人工导入或按同一请求录入上游成本，建立 verified/estimated/unmatched 状态和关联证据。

### P2：后端聚合

按北京时间范围和用户/模型/线路维度聚合收入、成本、毛利、覆盖率；加入退款、失败和重复记录防护。

### P3：管理页面

实现日期、日/周/月粒度、账号筛选、模型/线路筛选、汇总卡、明细下钻和未匹配清单。

### P4：自动同步与验收

在上游具备稳定只读日志/API 后自动同步成本；用同一请求样例、边界日期、退款和未匹配场景完成验收。自动同步未完成前，报表必须明确标注“部分为估算”。

## 11. 待后续确认的问题

- 上游是否能稳定提供逐请求费用和可关联 Request ID；
- GPT Pro 的 0.13 成本如何从供应商账单逐笔核验；
- 上游充值优惠、赠送余额、退款是否改变有效 ¥/上游$；
- 是否需要 CSV 导出和定时日报；
- 是否需要在毛利之外增加支付手续费、服务器和税费的净利润视图。
