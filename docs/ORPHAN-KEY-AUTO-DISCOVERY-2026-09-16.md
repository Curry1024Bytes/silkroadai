# 遗留 Key 自动识别与失效归档

## 目的与操作

operator 已先删除 new-api 分组，再来清理 Portal 时，不应要求记住原来的准确分组名。本批沿用「做好并测试通过后直接上线」授权，在 dev 完成后按 dev → prod → VPS 发布；main 不参与项目改动。

「删除任务与遗留 Key」点击清理后自动预览，不再手填分组名。尚存 Key 按 Portal 保存的客户/token 绑定读取当前实际 group，并展示来源及清单；确认后仍走持久化撤销任务。若所有远端记录均已缺失，核验客户身份及旧凭据拒绝后，仅归档失效 Key。后者不发送 DELETE，不虚构 group，也不会把未知名称替换为 default。

当前 Key 分组不是原分组历史的证明。若已有匹配客户/token/凭据摘要的非遗留删除任务历史，则核对历史；历史冲突、多组、其他启用档占用、身份不明一律阻止自动清理。没有历史时明确展示「当前归属」，仍需核对清单确认。执行前再次检查实际归属；new-api 原生后台不共享 Portal 协调锁，不能宣称跨系统原子操作。

## 实现边界

- 识别只使用 GET 客户身份/token 元数据及不计费的凭据检查，不调用模型，不轮换凭据。所有目标从当前租户 Portal 持久记录读取，平台 null/UUID 的兼容及其他租户隔离保留。
- 归档模式进入签名、持久任务及恢复校验。预览、提交、继续均核验远端缺失和凭据拒绝；记录重现、缓存仍接受或未知响应不能计为完成。归档任务出现 DELETE 意图或远端存在证据时拒绝继续。
- 任务仍逐 Key 恢复，完成提示区分真实撤销与原已失效。已存在的普通任务继续兼容；旧显式 group 预览请求保留。
- 无 migration、依赖、环境变量、new-api 源码、计费、Nginx 或 Cloudflare 改动。生产仍为79条migration。发布功能不代替管理员确认历史 Key 撤销，本次不执行真实遗留 Key 清理。
