# 动态模型成本、统一售价与客户专属折扣需求

- 创建日期：2026-11-05（Asia/Shanghai）
- 状态：需求已确认，2026-11-05 起开发
- 适用项目：LLmRoute Portal
- 目的：统一记录 operator 已明确的业务需求，作为后续实现和验收依据。

## 1. 需求概述

平台通过多个分组/渠道采购模型服务。一个分组/渠道可以包含多个模型，同一模型在不同渠道的采购成本也可能不同。平台需要按“分组/渠道 + 模型”独立维护采购成本和对客价格，并支持对所有用户设置统一售卖规则，以及对特定客户在该分组/渠道下的特定模型设置专属折扣。

上述规则必须影响客户真实请求的最终扣款。仅保存规则、展示目录价、报价预览或修改管理页面，不算需求完成。

## 2. 业务目标

1. 支持所有已接入模型，不限于视频模型或某个固定模型系列。
2. 对每个分组/渠道中的每个模型分别维护采购成本；不同模型和不同渠道之间互不串用。
3. 能为每个分组/渠道中的每个模型设置面向所有用户的统一售卖价，并可在其上设置全局售卖折扣。
4. 能为指定客户设置该分组/渠道下一个或多个模型的专属折扣；每个模型可独立配置。也能为指定客户设置该分组/渠道下全部模型的客户统一折扣。
5. 规则命中和金额计算在实际扣款入口生效，并能由订单、用量或账本记录核验。
6. 保留规则变更历史，发布前能查看影响范围、成本、售价和毛利。

## 3. 核心定价身份

每条成本或售价规则必须唯一对应以下业务身份：

`分组/渠道 + 模型 + 计费规格（适用时）`

- 分组/渠道应使用系统中稳定的 ID 或规范化标识，不能只依赖显示名称。
- 售价规则中的“分组/渠道”指 Portal 档次。一个档次可拆成多个 new-api 计费分组，每个“档次 + 模型”只落在其中一个计费分组。采购成本按渠道记录。见 11.3。
- 模型应关联目录模型 ID 和已登记的上游模型映射；显示名或请求中的原始模型名不能单独充当跨渠道唯一键。
- 分辨率、时长、质量、输入/输出 token 等影响成本或计费的规格，应作为计费维度纳入身份或价格规则。
- 新增模型、渠道或规格应通过现有动态目录/映射机制登记，不要求为每个模型名称新增代码分支。
- 映射缺失、重复或有歧义时，应拒绝发布或收费并返回可诊断错误；不得猜测其他渠道或模型的价格。

## 4. 成本与全局售卖规则

### 4.1 采购成本

- 每个“渠道 + 模型 + 计费规格”可独立记录采购成本及其币种、单位、来源和生效时间。
- 当供应商给出基准价和采购折扣时，应能表达并展示最终有效采购成本；采购折扣与客户售卖折扣是两种不同规则，不能混为一谈。
- 按模型实际计费方式支持成本输入与计算，例如 token、图片、视频时长/规格或其他已验证单位；不得把所有视频价格一律假设为按秒计费。
- 成本变更应形成新版本并保留历史记录。只保存成本或试算，不得暗中改变客户实付价格。

### 4.2 面向所有用户的售卖规则

- 管理员可对每个“分组/渠道 + 模型 + 计费规格”设置统一售卖价，并可在统一售卖价上设置全局售卖折扣。统一售卖价是未命中任何折扣的客户实付的价格，也是各类折扣的计算基准。
- 统一售卖规则适用于该规则覆盖范围内的所有客户；不得因客户、模型别名或渠道映射而意外扩大范围。
- 管理员可查看生效价格、价格单位、成本版本、毛利金额和毛利率。同一计费分组内有多个渠道提供同一模型时，毛利按成本最高的渠道计算。
- 价格发布需预览受影响的模型、渠道、规格、计费入口和客户范围，并记录发布人、时间、前后值及结果。

## 5. 客户专属折扣

- 管理员可选择客户、分组/渠道和模型，为该客户设置该模型的专属折扣。
- 同一客户在同一分组/渠道下可以对不同模型设置不同折扣；某模型的配置不得自动套用于该分组的其他模型。
- 管理员也可为客户设置某分组/渠道下的客户统一折扣。它作用于该客户在该分组/渠道下的全部模型，包括之后新增的模型；某模型设有客户专属折扣或全局售卖折扣时，按第 6 节的命中顺序计价。
- 可以新增、修改、停用或清除单条客户模型规则或客户统一折扣；清除后按第 6 节的命中顺序回落。
- 规则详情及价格预览应显示客户、分组/渠道、模型、折扣值、生效时间和最终命中的规则来源。
- 客户专属折扣必须使用规范化模型身份匹配。同名模型跨渠道或跨规格时必须隔离。

## 6. 折扣口径与命中顺序

- 管理页面以百分比呈现折扣，并明确“按标价的 80% 收费”表示实付为该身份统一售卖价的 80%。后端应使用统一的数值口径和精度校验，折扣倍率须在 0.05 至 2 之间，含两端；禁止零、负数和非有限值。最终价低于当前采购成本时，发布前须由发布人二次确认并填写原因。
- 对同一请求只选择一条有效售卖折扣，乘在该身份的统一售卖价上；不把全局折扣、客户统一折扣与客户专属折扣相乘，以免意外叠加降价。
- 命中顺序：
    1. 精确匹配的“客户 + 分组/渠道 + 模型 + 计费规格”专属折扣；
    2. 该“分组/渠道 + 模型 + 计费规格”的全局售卖折扣；
    3. 该客户在该分组/渠道下的客户统一折扣；
    4. 该身份的统一售卖价（不另应用折扣）。
- 全局售卖折扣优先于客户统一折扣。发布或修改全局售卖折扣时，若某客户的客户统一折扣收费比例更低，例如全局按 90% 收费、该客户统一折扣按 80% 收费，该客户的实付会上涨；发布预览须单独列出这些客户及涨幅，由管理员确认后才能发布。
- 某身份的统一售卖价调整时，在该身份上享有客户专属折扣或客户统一折扣的客户，实付同比例变化；发布预览须列出这些客户及调整前后的价格。
- 任一层规则不存在、已停用或已过期时，继续按上述顺序回落；不能继续使用过期值。
- 规则可设生效和到期时间；本次不支持按星期或每日时段的促销。new-api 分叉自带的每日限时折扣不由 Portal 管理，不能与客户专属折扣或客户统一折扣同时作用于同一计费分组内的模型，见 11.6。
- 同一层内，更具体的规则优先，例如单规格规则优先于整模型规则。同样具体的多条有效规则互相冲突时，应拒绝保存或收费并明确指出冲突，不能依赖数据库返回顺序。单规格规则要求该规格有独立的模型名，见 11.7。
- 最终计价、目录展示、价格预览与账单记录应能说明使用了哪一个身份、成本版本、售价和折扣来源。

## 7. 实际扣款范围与责任边界

所有面向客户收费的入口均属于需求范围，包括但不限于：

- Portal 自有账本或由 Portal 代理执行的扣款；
- new-api 用户 API Key 直接调用并扣除 new-api 用户额度的请求；
- 图片、视频及其他具有独立计费单位或异步结算流程的模型请求。

企业门户、Batch、Portal 自有账本计费，以及主站 Portal 的 Seedance 和 Kling 自扣视频，暂不纳入本次实现和验收，前提是它们在生产中未启用；这些入口启用前须满足本规格并单独验收，见 11.9。

每个入口必须明确唯一的扣款责任方、模型身份解析方式、规则读取时点、幂等键、失败行为和账单证据。不得对同一请求重复扣款，也不得通过 Portal 事后补扣掩盖上游账单未按规则计价。

项目约束是不修改 new-api 源码，包括生产运行的自维护分叉 `new-api-custom-full`，见 11.1。对于由 new-api 实际扣款的入口，必须验证现有接口或配置确实能表达并执行“客户 + 分组/渠道 + 模型”的价格差异。Portal 页面、目录价格或配置写入成功不能代替真实扣款证据。若某入口的现有计费能力无法满足规则粒度，该入口仍属于未满足，不能以 Portal 自有账本测试替代验收。

## 8. 管理操作、安全与审计

- 成本编辑、价格预览、正式发布和客户折扣修改应具有清晰且不同的操作语义。
- 所有输入均由服务端校验；客户端试算结果不能作为最终扣款依据。
- 并发编辑、旧版本提交或过期预览不得覆盖更新的配置。
- 保留成本、售价和折扣的历史版本及操作审计；停用或清除活动规则不得删除历史账单所需的数据。
- 审计信息应包括操作者、变更时间、规则身份、前后值、变更原因和发布/执行结果；日志不得记录 API Key 等秘密。
- 价格写入结果不确定时，先核验实际生效配置再恢复或重试，不得盲目重复写入。

## 9. 验收标准

1. 管理员可在同一分组/渠道下为至少两个不同模型设置不同采购成本和对客价格；修改一个模型不会改变另一个模型或其他渠道的价格。
2. 统一售卖规则对所有适用客户生效；客户统一折扣只影响指定客户在指定分组/渠道下的模型；客户专属折扣只影响指定客户、分组/渠道、模型和计费规格。
3. 按客户专属折扣、全局售卖折扣、客户统一折扣、统一售卖价的顺序命中，命中的折扣乘在统一售卖价上，规则之间不连乘；清除或过期后正确回落；统一售卖价调整时，享有客户折扣的客户同比例变化；全局售卖折扣导致部分客户涨价时，发布预览列出这些客户。
4. 使用真实扣款入口验证最终收费金额，并能在相应账单、用量或账本记录中核对命中的模型身份和折扣来源。
5. 覆盖当前所有启用模型及其实际计费方式，包括 token、图片、视频和其他已接入模态；不能只以 Seedance 或单一视频模型通过验收。
6. 对 Portal 与 new-api 两种扣款责任分别提供验证证据；未能按“客户 + 分组/渠道 + 模型”执行的入口明确列为未完成，不能宣称整项需求满足。
7. 映射歧义、非法价格/折扣、规则冲突、配置并发或发布失败时，不会以更低的猜测价格继续收费，也不会发生重复扣款。
8. 价格与折扣历史、操作审计和发布结果可查询；自动化测试及项目要求的类型检查、lint、格式检查、数据库校验和生产构建通过。
9. 生产验收不得擅自改价或发起收费测试；需要收费验收时，按已明确的测试客户、模型、预算和请求范围执行并记录结果。

## 10. 当前已知差距

根据截至 2026-11-05 的当前代码检查结果：

- 成本工作台已有部分模型和计费类型的成本维护、试算及发布能力；视频成本目前可以保存和试算，但售价发布会被明确拦截。
- Enterprise Seedance 视频路径已有特定的客户模型折扣和全局折扣规则，但其身份范围不是所有动态模型、渠道和计费规格的通用实现。
- 普通 new-api API Key 的客户费率当前以分组倍率为主，不能据此认定支持同一分组内按客户、按模型分别折扣。
- 通用目录折扣选择逻辑存在，但当前代码搜索未发现其已接入全部实际扣款入口。

以上是代码层检查结论，不代表已核验当前生产数据库、线上价格或所有部署版本。实现和发布前须重新核对代码版本及实际配置。

### 10.1 2026-11-05 补充核查

依据：`dev@f219384f` 代码、[部署与运维手册](../../../deploy/部署与运维手册.md)、`new-api-custom-full` 已提交源码，以及 operator 在生产服务器执行的只读命令输出。未查询生产数据库，未核对线上价格配置。

1. 生产 new-api 运行 `new-api-custom-full` 的 `main@8c02661`（2026-09-29 提交），镜像 `new-api-custom:latest` 构建于 2026-10-10，容器创建于 2026-10-12。二进制不含提交号，`/api/status` 版本号为空；判断依据是二进制中出现自该提交起才有的代码字符串，没有 `289febd` 及开发机未提交改动才有的字符串，且 `/opt/new-api` 源码文件时间与该提交时间一致。这是特征比对，不是逐字节复现；2026-10-29 的 `289febd` 未部署。
2. new-api 每次扣费 = 模型价格 × 分组系数 × 限时折扣。模型价格按客户请求的模型名查找，所有分组和客户共用；渠道模型映射发生在计价之后。分组系数依次取分组内用户专属倍率、用户分组对计费分组倍率、计费分组倍率中第一个存在的值，不相乘。限时折扣按模型名设置一个北京时间每日时段，对所有分组和客户生效，并与分组系数相乘。
3. 计费表达式可读取 token 与媒体用量、请求头、请求参数、任务用量和时间，结果仍乘以分组系数。表达式没有分组、客户或渠道变量；任务用量只由 Task Plugin 渠道提供。因此 new-api 原生不能按“分组 + 模型”或“客户 + 模型”定价。分组内用户专属倍率和限时折扣是该分叉自行加入的功能。
4. Portal 发布统一售价时按模型名写入 new-api 的全局价格，同名模型的各档次一起更新，预览会提示其他渠道中同名模型的请求也受影响。按分组改倍率则会同时改变该分组的全部模型。两者都与第 9 节验收标准 1 冲突。
5. 主站客户专属分组倍率按“客户 + 档次”写入用户分组对计费分组倍率，对该档全部模型生效。Portal 不读取也不管理分组内用户专属倍率；Portal 定价后台在模型开启限时折扣时只提示“实际扣费会更低”，显示价不含该折扣。生产是否配置了这两项未核对。
6. 通用目录折扣选择逻辑（`src/lib/billing/catalog-discounts.ts`）只有测试调用，未接入任何扣款入口。多条全局规则同时命中时，它按范围具体程度、优先级和创建时间选出一条，与第 6 节“同优先级冲突应拒绝”不一致。
7. 成本工作台把视频规格一律按秒计价，与第 4.1 节不一致；成本规则只有修订号，没有生效时间字段。
8. Portal 自有账本的计量只计输入和输出 token，不含图片、缓存、阶梯价和视频。按 2026-08-05 与 2026-09-09 的发布记录，生产未开启 Portal 自有账本计费，用户均为 `billing_mode=newapi`。
9. 企业门户的计费与折扣逻辑只在 `PORTAL_FLAVOR=seedance-enterprise` 实例运行；当前服务器只部署主站 Portal。`6d3abf8b` 与 `249d7137` 的企业折扣改动不在当前生产的扣款路径上。
10. 公网 API 域名只把 `/v1/`、`/v1beta/` 和两条方舟视频任务路径转给 Portal；new-api 只绑定内部地址，不直接对外。
11. 现有[实施计划](../plans/2026-11-04-dynamic-model-cost-discounts.md)按 2026-11-04 版规格编写，在扣款范围、命中层级（客户统一折扣、时段促销）和同层冲突处理上与本规格不一致，开发前须重写。

### 11.2 new-api 扣款入口如何满足“客户 + 分组/渠道 + 模型”粒度

现状见 10.1 第 2 至 5 条。可选做法：

1. 专属模型别名：Portal 按 Key 归属把请求里的模型名改写成专属别名，new-api 按别名单独计价扣费。每个专属价都要登记别名、渠道模型、模型映射和价格；响应和流式数据要改回公开名；目录、`/v1/models` 和用量展示须隐藏别名。2K/4K 图片折扣 SKU 已用“别名单独定价、渠道映射回真名”的机制，但不分客户。
2. 可信请求头加计费表达式：Portal 按 Key 归属注入请求头，new-api 计费表达式按该头分支计价。Portal 目前除连接类请求头外原样转发客户请求头，必须无条件覆盖同名头，否则客户可冒用他人价格。现有表达式校验只支持按输入长度分档的线性 token 公式，需要扩展；视频的表达式计费目前只在 Task Plugin 渠道可用，其他模态须逐一验证。
3. Portal 自有账本：扣款责任方改为 Portal，new-api 额度只做准入。须先补齐图片、缓存、阶梯价和视频计量，保持全局计费开关与客户计费模式一致，并接受按轮询周期事后记账带来的透支窗口。还须在第 7 节写明这是扣款责任方变更，区别于“Portal 事后补扣掩盖上游账单”。
4. 在 new-api 分叉内原生实现：仅当 11.1 允许修改分叉时可选。
5. 接受该入口不满足：按第 9 节验收标准 6 列为未完成，整项需求不能标记为已验收。
6. 按需拆分计费分组：需要独立价格的“分组 + 模型”单独成为 new-api 的一个计费分组，独立价格体现在该分组倍率上。客户专属折扣写入客户专属分组倍率，替换该分组倍率，不相乘。客户的 Key 可包含多个计费分组，new-api 按顺序选第一个有可用渠道的分组，并按该分组扣费。Portal 保存规则，发布时按命中顺序算出每个“客户 + 计费分组”的最终倍率并写入 new-api；new-api 实时扣款，日志记录所用分组、实际生效的分组倍率，以及命中的客户专属倍率和限时折扣。不改写模型名，也不修改 new-api 源码。上游 yexioy/silkroadai 主站用同一机制：客户专属价写在分组倍率矩阵里，模型差价靠拆分组。

做法 1 和 2 依赖所有客户请求都经过 Portal（见 10.1 第 10 条），专属价仍会再乘分组系数。

- 待确认：采用哪一种或哪几种组合，以及每个入口的扣款责任方。
- 确认结果：operator 于 2026-11-05 确认采用做法 6。由 new-api 扣款的入口继续由 new-api 扣款；Portal 自扣的入口仍由 Portal 扣款，是否纳入本次验收见 11.9。

采用做法 6 的约束：

1. 渠道挂到分组后，其全部模型都进入该分组。要单独给某个模型定价，就要复制一份只列该模型的渠道；上游 Key 变化时，每份副本都要同步。
2. 同一模型在一个 Key 的各计费分组中只能出现一次。否则专属分组没有可用渠道时，请求会落到其他分组，按错误的价格扣费；Portal 发 Key 时须校验。
3. Portal 目前一个 Key 只有一个档次、一个渠道只能属于一个启用档次、建 Key 只下发一个分组，这些都要调整；受影响的已发 Key 要迁移或重发。
4. 改价调整对应计费分组的倍率。按模型名共享的基础价格会同时改变所有分组的同名模型（见 10.1 第 4 条），只用于全平台统一调整。
5. 折扣粒度到“客户 + 计费分组”，同一分组内的模型共用折扣。规格级折扣要给该规格独立的模型名（见 11.7）。
6. 有生效或到期时间的规则要定时重新发布，边界前后会短暂沿用旧值。第 6 节不允许继续使用过期值，开发设计须确定提前发布切换，还是接受明确的最大延迟。
7. new-api 分叉的限时折扣会与客户专属分组倍率相乘，同一模型不能同时使用两者（见 11.5、11.6）。
8. 客户专属分组倍率是全局配置，没有乐观锁，写入须沿用现有定价协调锁。
9. 分组内用户专属倍率的优先级高于客户专属分组倍率，Portal 目前不读取它；发布核对时要确认 Portal 写入的倍率没有被它覆盖。

将来如果需要大量按规格、按客户定制价格，拆分组会难以维护，届时再评估做法 3。

### 11.3 “分组/渠道”指哪一层

- 现状：Portal 档次对应 new-api 的一个分组，一个分组可以包含多个渠道。new-api 只按分组取系数，不区分渠道。成本规则按“模型 + 档次”保存，并通过模型映射绑定该档内的一个渠道。
- 待确认：成本按渠道还是按分组记录；同一分组内多个渠道提供同一模型且成本不同时，以哪个渠道的成本计算毛利。档次现有的进货率在多上游时取最贵者，可作参照。按 11.2 做法 6，售价按计费分组设置。
- 确认结果：operator 于 2026-11-05 确认售价规则中的“分组/渠道”指 Portal 档次。一个档次可按 11.2 做法 6 拆成多个计费分组，每个“档次 + 模型”只落在其中一个计费分组。采购成本按渠道记录。同一计费分组内有多个渠道提供同一模型时，按成本最高的渠道计算毛利，也按它做 11.8 的低于成本检查，因为发布前无法确定 new-api 会选哪个渠道；档次现有的进货率也取最贵者。已据此回写第 3、4.1、4.2 节。

### 11.4 折扣基准价

- 现状：主站档次价 = 官方基础价 × 分组系数；企业门户实付 = 官方挂牌价 × 折扣。2026-11-04 版规格以“模型默认售价”为基准。
- 待确认：第 6 节的“标价”和第 4.2 节原有的“基础价”指官方挂牌价，还是该分组的统一售卖价。两者结果不同：官方价 ¥10、分组系数 1.2、客户折扣 80% 时，前者实付 ¥8，后者实付 ¥9.6。
- 确认结果：operator 于 2026-11-05 确认两者都指该身份的统一售卖价，即未命中任何折扣的客户实付的价格。客户专属折扣、全局售卖折扣和客户统一折扣都乘在统一售卖价上，同一折扣在各分组含义一致，单独定价模型的差价得以保留。主站的统一售卖价 = 官方基础价 × 计费分组倍率，官方基础价仍是共用的计价成分，不作折扣基准。已据此回写第 2、4.2、6、9 节和 11.5 的约束 3。

按 11.2 做法 6 落地的约束：

1. Portal 须为每个计费分组单独保存与统一售卖价对应的分组倍率，下称统一售卖倍率。全局售卖折扣生效期间，写入 new-api 的是统一售卖倍率 × 全局折扣，结束后恢复为统一售卖倍率，所以 new-api 的当前值不能当作统一售卖倍率。Portal 目前换算档次价时直接读取 new-api 的当前分组倍率，开发时须改为读取统一售卖倍率。
2. 客户专属分组倍率 = 统一售卖倍率 × 命中的客户折扣。若用已含全局折扣的当前倍率计算，全局折扣会与客户折扣相乘，违反第 6 节。
3. 调整统一售卖倍率时，new-api 中的客户专属分组倍率是绝对值，不会自动跟随。Portal 须同时重写该计费分组内所有享有客户折扣的客户的倍率，否则这些客户停在旧价。按模型名共享的官方基础价调整时，各分组和客户按比例一起变化，不需要重写。

### 11.5 客户统一折扣层是否保留

- 现状：第 6 节原有的命中顺序没有“客户统一折扣”这一层，但企业门户按“客户 + 区域”设有整体折扣，主站按“客户 + 档次”设有专属分组倍率，new-api 分叉还支持分组内用户专属倍率。直接去掉会让已配置的客户回落到统一售价。另外，new-api 的限时折扣会与客户专属分组系数相乘。
- 待确认：保留、去掉，还是并入客户专属折扣；若保留，排在全局售卖折扣之前还是之后（企业门户现为全局折扣优先）。限时折扣与客户专属分组倍率相乘的处理见 11.2 做法 6 的约束 7。
- 确认结果：operator 于 2026-11-05 确认保留客户统一折扣，范围是该客户在某分组/渠道下的全部模型，与全局售卖折扣同时命中时全局优先。命中顺序为客户专属折扣、全局售卖折扣、客户统一折扣、统一售卖价，与企业门户现行代码和 2026-11-04 版规格一致。全局售卖折扣的收费比例高于某客户的客户统一折扣时，该客户会涨价，发布预览须列出这些客户。已据此回写第 2、5、6、9 节。

按 11.2 做法 6 落地的约束：

1. 发布时，Portal 把客户统一折扣展开到该分组/渠道对应的每个计费分组，写成该客户的客户专属分组倍率。已有全局售卖折扣的计费分组不写入客户统一折扣，让 new-api 回落到含全局折扣的分组倍率；该客户在某计费分组有客户专属折扣时，写入专属折扣。
2. 新增或拆分计费分组，以及全局售卖折扣开始、结束或修改时，Portal 须重算并重写受影响客户的客户专属分组倍率。否则客户会在新分组上静默失去统一折扣，或留下覆盖全局折扣的旧倍率。开始和结束的时点按 11.2 做法 6 的约束 6 处理。
3. 主站现有的客户专属分组倍率按“客户 + 档次”设置，迁移后归入客户统一折扣。它是绝对值，直接替换分组倍率，以后调整分组倍率时不跟随；按 11.4 改成相对统一售卖价的折扣后，客户价格会随该档统一售卖价同比例变化。折扣 = 原倍率 ÷ 换算时该档的统一售卖倍率。换算后重新算出的倍率应与现值一致；因取整等原因不一致的客户，要在发布预览中列出。

### 11.6 星期与时段促销是否保留

- 现状：2026-11-04 版规格要求按星期和每日时段促销，企业门户已实现日历式全局折扣，但未部署。new-api 分叉自带按模型的每日限时折扣，只有一个北京时间时段、不分星期，作用于全部客户。本规格未提时段促销。
- 待确认：保留并扩展到全部模型，还是移出本需求；若保留，规则按请求受理时点还是结算时点读取。new-api 的阶梯计费在预扣时冻结限时折扣。按 11.2 做法 6，Portal 侧的时段规则要靠定时重新发布生效（约束 6）。
- 确认结果：operator 于 2026-11-05 确认按星期和每日时段的促销移出本需求，与 11.1 不修改分叉一致。规则仍可设生效和到期时间，按 11.2 做法 6 的约束 6 定时重新发布。new-api 分叉自带的每日限时折扣保留为 new-api 的现有功能，不由 Portal 管理。按约束 7，Portal 发布客户专属分组倍率时，若对应计费分组内有模型开启了限时折扣，须拒绝发布。已据此回写第 6 节。

### 11.7 折扣能否细到计费规格

- 现状：第 6 节命中顺序把计费规格纳入身份，但企业门户的折扣只按区域和模型档位匹配，不区分分辨率等规格。成本工作台的规格可区分分辨率、声音和参考视频。new-api 可对图片和视频任务按分辨率分别定价，但仍按模型名共享并乘以分组系数。按 11.2 做法 6，规格级折扣要给该规格独立的模型名。
- 待确认：客户专属折扣和全局售卖折扣能否只作用于某一规格；整模型规则与单规格规则同时存在时，按同优先级冲突拒绝，还是更具体的规则优先。
- 确认结果：operator 于 2026-11-05 确认折扣可只作用于某一计费规格。同一层内更具体的规则优先，只有同样具体的重复规则才拒绝，结果不依赖数据库顺序。按 11.2 做法 6，单规格规则要求该规格有独立的模型名；没有独立模型名的规格不能单独设折扣，保存时拒绝并说明原因。已据此回写第 6 节。

### 11.8 折扣倍率的允许范围

- 现状：企业门户允许 0.05 至 2；主站客户专属分组倍率允许大于 0 且不超过 100；new-api 限时折扣允许大于 0 且不超过 1，分组内用户专属倍率允许 0 至 1000，其中 0 即免费，与第 6 节“禁止零”冲突。成本工作台要求售价倍率不低于上游倍率，但客户折扣作用在售价之后，实付仍可能低于采购成本。
- 待确认：第 6 节“平台价格政策”允许的范围；能否高于标价；能否低于采购成本，若能由谁审批。
- 确认结果：operator 于 2026-11-05 确认折扣倍率全平台统一为 0.05 至 2，含两端，禁止 0。倍率大于 1 即高于统一售卖价，最高为其 2 倍。最终价低于当前采购成本时，发布前须由发布人二次确认并填写原因，记入审计；采购成本按 11.3 取成本最高的渠道。主站现有客户专属分组倍率换算成折扣后若超出此范围，迁移时列出，由管理员处理，不自动截断。已据此回写第 6 节。

### 11.9 尚未启用的扣款入口是否纳入本次验收

- 现状：企业门户实例未部署；Batch 默认关闭；生产未开启 Portal 自有账本计费；Seedance 自扣视频所需的上游密钥按记录未配置；Kling 自扣视频的生产配置未核对。
- 待确认：这些入口本次实现并验收，还是先不纳入，改为“启用前须满足本规格”。
- 确认结果：operator 于 2026-11-05 确认企业门户暂不纳入本次实现和验收。Batch、Portal 自有账本计费，以及由主站 Portal 的 `/v1` 处理的 Seedance 和 Kling 自扣视频，本次也不纳入实现和验收，前提是它们在生产中未启用；这些入口启用前须满足本规格并单独验收。Kling 自扣视频的生产配置尚未核对，若核对发现已启用，它不适用本条，处理方式须另行确认。已据此回写第 7 节。
