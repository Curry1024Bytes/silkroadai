## 1. 提示的含义

这条提示不是报错。同步本身没有变化，只是 Portal 读不懂这 6 个模型在 new-api 里的计费公式，所以跳过它们：不上架，也不更新价格。

- 客户调用和扣费不受影响，new-api 照常按自己的公式计费。
- 这 6 个模型不在 Portal 目录里：模型列表、`/pricing`、定价页都看不到，也不能在 Portal 改价。
- 每次同步都会出现这条提示，直到 Portal 支持这两类写法。

报错位置：解析器 `src/lib/admin/pricing-tiered-expression.ts:93`，同步拒绝文案 `src/lib/newapi/catalog-sync-advanced.ts:168`。Portal 的阶梯解析器只认 `len <= N ? tier(...) : ...` 这一种写法，其中只能出现 `p`、`c`、`cr`、`cc`、`cc1h` 的线性单价；遇到任何别的写法就整条拒绝，不做近似。

## 2. 线上计费写法分布（2026-11-06 13:41，new-api `/api/pricing`）

| 计费写法                                   | 模型数 | 例子                                   | Portal 能同步 |
| ------------------------------------------ | ------ | -------------------------------------- | ------------- |
| 按 Token 倍率                              | 16     | Claude 系列                            | 能            |
| 视频按条 / 按秒                            | 13     | video-v2、wan-3.0、MiniMax-H3          | 能            |
| 按次固定价                                 | 8      | 图片模型                               | 能            |
| 按输入长度分档                             | 4      | gpt-6 系列                             | 能            |
| 图片分项 Token（`img`）                    | 3      | gpt-image-2                            | 能            |
| 按任务参数分档（`u(...)`）                 | 4      | doubao-seedance-*                      | **不能**      |
| 按时间分档（`now()`/`weekday()`/`hour()`） | 2      | deepseek-v4-flash、deepseek-v4.1-flash | **不能**      |

结论：以后新接的模型和渠道要不要开发，取决于计费公式的写法，和模型、渠道本身无关。用上表前 5 种写法的不需要开发。

需要注意的来源：

- 我们自己在 new-api 写的公式（如 Seedance）可以选 Portal 认识的写法。
- 用 new-api「上游价格同步」原样拷来的公式（如 DeepSeek 拷 aipg），上游写成什么样我们就收到什么样，仍可能出现新写法。
- 不认识的写法不会默默出错：同步预览会在黄色提示框里逐个列出，模型不会带错误价格上架。

## 3. 现有两类不支持写法的实况

### 3.1 Seedance（渠道 #13，分组 `SD官转`，GroupRatio 7.5）

四个模型结构完全相同：8 档 = 分辨率 4 种 × 是否带参考视频 2 种，每档 `u("tokens") * 单价 / 1000000`。最后一档 `tier("4k·video", ...)` 不带条件，是兜底分支。

```
u("resolution") == "480p" && u("video_input") == "none" ? tier("480p·none", u("tokens") * 6.14 / 1000000) : ... : tier("4k·video", u("tokens") * 2.14 / 1000000)
```

`billing_usage_schema` 已列出参数及可选值：`resolution` ∈ {480p, 720p, 1080p, 4k}，`video_input` ∈ {none, video}，`tokens` 为数量。

当前系数（= 官方价 ÷ 7.5，两位小数进 1）：

| 模型                            | 480p/720p 无视频 / 有视频 | 1080p 无 / 有 | 4k 无 / 有   |
| ------------------------------- | ------------------------- | ------------- | ------------ |
| doubao-seedance-2-0-260128      | 6.14 / 3.74               | 6.8 / 4.14    | 3.47 / 2.14  |
| doubao-seedance-2-0-fast-260128 | 4.94 / 2.94               | 5.4 / 3.27    | 5.4 / 3.27   |
| doubao-seedance-2-0-mini-260615 | 3.07 / 1.87               | 3.4 / 2.07    | 3.4 / 2.07   |
| doubao-seedance-2-5-260628      | 9.34 / 5.6                | 10.27 / 6.14  | 10.27 / 6.14 |

`src/lib/seedance/cn-billing.ts` 里 fast、mini、2.5 没有 4k 挂牌价，公式里这三个模型的 4k 档沿用 1080p 单价。

### 3.2 DeepSeek（渠道 #14，分组 `DeepSeek`，GroupRatio 0.7）

公式从 aipg 原样同步：先排除国庆假期（`date("2026-10-01…")` 到 `date("2026-10-08…")`，已过期但仍在公式里），再判断工作日北京时间 9–12、14–18 为高峰。高峰 `p*2 + cr*0.04 + c*8`，低谷 `p*1 + cr*0.02 + c*4`，低谷正好是高峰的一半。

## 4. 推荐方案

### 4.1 Seedance：按通用参数矩阵格式支持

不把参数名 `resolution` / `video_input` 写死在代码里，而是支持「若干枚举参数组合 × 线性单价」这一整类写法：

- 条件只允许 `u("参数") == "字面量"`，多个条件用 `&&` 连接；参数名和可选值从 `billing_usage_schema` 读取。
- 每档只允许 `u("数量参数") * 单价 / 常数`，单价必须是非负数字字面量。
- 完整性检查：schema 列出的每种参数组合必须恰好命中一档；不带条件的兜底分支只能对应剩下的唯一组合，否则整条拒绝。
- 严格程度与现有阶梯解析器一致：格式不符就整条拒绝，进同步提示框，不猜价格。

和只认 Seedance 两个参数相比，多出的工作量主要在测试；好处是以后按其他参数（如时长、是否有声）查表定价的模型不用再开发，并且完整性检查对 Seedance 本身也有用。线上目前只有这 4 个模型用这种写法，以后是否会出现更多同类模型尚不确定。

### 4.2 DeepSeek：继续在 new-api 维护

时间条件、非线性计算和自定义函数做成通用支持成本高、容易出错，不建议做。只把同步提示改成「已知，在 new-api 维护」，不再标成需要核对。

备选（未决定、未验证）：低谷价正好是高峰价的一半，理论上可改写成「基础价 + new-api 分时折扣」，Portal 已能读分时折扣。代价是以后 aipg 调价不能直接同步过来；也还没验证 new-api 的分时折扣能否准确表达周末全天这个时间段。

### 第 3 步：切换到逐模型售价（生产操作，需逐步核对）— 待办
