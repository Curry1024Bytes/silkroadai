# 视频模型兼容1.0

日期：2026-10-28（北京时间）。本文说明如何把新的视频上游接进 new-api 并通过 Portal 售卖：按上游协议选渠道类型，配置按秒或按次价格，同步目录，再用真实任务验收。

依据：new-api-custom-full `8c0266135559e5fe996e3abb803f4e347a6b8b63` 源码（[部署与运维手册](../deploy/部署与运维手册.md) 0.4 节的目标版本）、本仓库 dev 分支源码，以及 2026-10-28 对生产 new-api 和 Portal 数据库的只读查询。期间没有修改任何配置；唯一的收费请求是 2.7 用上游 Key 直接打上游的一条实测任务。2026-10-29 补充 2.7 的路由差异、2.8 的 Portal 原生入口，以及第 6 节的上架配置和首条真实任务验收。

## 1. 接入前向上游确认

- 接口：提交和查询的路径、状态取值、成片地址在返回里的哪个字段、返回里有没有 usage。
- 计费：按 token、按秒还是按次；完整价目表，包括各分辨率档和是否含参考视频。
- 能力：模型名、支持的分辨率、时长、比例，参考图、视频、音频的数量上限。
- 成本：充值兑换比例和折扣，用来定第 4 节的分组倍率。

### 2.1 计费表达式只对 Task Plugin 生效

视频任务提交时，表达式拿到的 token 参数是空的，`p`、`c` 恒为 0。表达式模式还要求渠道上报用量字段，只有 Task Plugin（65）满足；其他视频渠道选了表达式，每次提交都返回 400 `model_price_error`。渠道绑定插件后，定价页会换成插件的用量字段。以 doubao 插件和 Seedance 2.5 官方价（元/百万 token）为例：

```text
u("resolution") == "1080p" && u("video_input") == "video" ? tier("1080p-video", u("tokens") * 46 / 1000000) : u("resolution") == "1080p" ? tier("1080p", u("tokens") * 77 / 1000000) : u("video_input") == "video" ? tier("video", u("tokens") * 42 / 1000000) : tier("base", u("tokens") * 70 / 1000000)
```

Portal 目录同步目前解析不了 `u(...)` 表达式，这类模型会显示「计费规则无法同步」，客户在目录里看不到价格，要等 Portal 补上支持。

### 2.2 DoubaoVideo（54）的 token 重算

以下按源码推断，本环境没有实测。价格填在「按 Token（已弃用）」。结算 quota = token 数 × ModelRatio × 分组倍率，所以每百万 token 售价（元）= 2 × ModelRatio × 分组倍率；只用 ModelRatio，不用补全倍率。提交时只预扣 ModelRatio ÷ 2 × 分组倍率 元，完成后按真实 token 重算。分辨率和含参考视频的倍率只对适配器内置价目表里的两个 2.0 模型生效，其他模型一律同价。

### 2.3 NewAPI Video（59）的计费分辨率

计费分辨率依次取 `metadata.resolution`、`metadata.quality`、`size`。没传 `size` 时，按比例换成 1280x720 等尺寸，即 720p。客户在顶层传的 `resolution` 会原样转发给上游，但不参与计费。所以一个模型名支持多种分辨率时，可能出的是 1080p、扣的是 720p。要按分辨率分档计价，优先用 60。

### 2.4 Openai Video（60）的成片地址与时长档位

- 解析结果时不读顶层 `data` 数组。如果上游只在 `data[0].url` 返回成片（xinhankr 文档写明就是这样，见 2.6），任务可能显示成功但没有地址。59 在轮询时会对整个返回体做一次深度扫描，能补上这个地址。
- 默认档位只收 5 到 30 的整数秒，不传时按 5 秒，分辨率不锁。「Seedance 2.5」档位把分辨率锁死在 720p。渠道没设视频档位时，模型名 `video-v3`、`seedance-2.5`、`sd2.5` 等会被自动当成 Seedance 2.5 档。

### 2.5 OpenAI（1）渠道上的视频任务

new-api 把类型 1 的视频任务交给内置 Sora 适配器：提交 `POST /v1/videos`，按 Sora 的状态值轮询，不读 usage，客户请求体除模型名外原样转发。按秒估价时没传秒数按 4 秒算；开启按分辨率计价时，客户要传 `size`、`metadata.resolution` 或 `metadata.quality` 之一，否则请求被拒。

### 2.6 xinhankr 的视频接口（2026-10-28 读取）

来源是 token.xinhankr.com 上两篇 tokensbyte 框架的预置文档（`is_preset=1`，最后更新于 2026-10-27）：「火山方舟原生接口」和「火山方舟视频」。页面 `/docs/...` 由前端渲染，直接抓取拿不到正文；目录在 `GET /api/v1/plugins/docs-api/public/tree?lang=zh`，正文在 `GET /api/v1/plugins/docs-api/public/docs/<数字 id>?lang=zh` 的 `content` 字段。页面地址里的 `doc0023` 对应 id 23。

- 火山方舟原生接口：提交 `POST /api/v3/contents/generations/tasks`，查询 `GET …/tasks/{task_id}`，取消 `DELETE …/tasks/{task_id}`，列表 `GET …/tasks`。用法是把 Base URL 指向这个平台、用平台的 Key，「无需改写为 OpenAI 格式」。推荐模型 `doubao-seedance-2-5`。文档没有给原生接口的返回样例，实测结果见 2.7。
- OpenAI 兼容接口：提交 `POST /v1/video/generations`，返回 `cgt-` 开头的任务号和 `pending`；查询和取消用 `/v1/video/generations/{task_id}`，也可用 `/v1/tasks/{task_id}`。完成时 `status` 为 `completed`，成片在 `data[0].url`；`usage` 在上游没回时为 0；失败时 `status` 为 `failed`，带 `error`。文档里没有 `/v1/videos` 路径。
- 2.5：时长 4 到 30 秒或 -1（模型自选），分辨率 480p、720p、1080p，比例 `21:9`、`16:9`、`4:3`、`1:1`、`3:4`、`9:16`、`adaptive`，参考素材最多 50 个（图 30、视频 10、音频 10）。编辑要求 `ratio=adaptive` 且 `duration=-1`；首帧、首尾帧、延长要求 `ratio=adaptive`。
- 2.0：时长 4 到 15 秒或 -1，分辨率可到 4k（fast、mini 不行），参考素材最多 15 个（图 9、视频 3、音频 3），不能只传音频。
- 错误码：402 是余额不足（不是 429）；429 是限频，或余额低时在途任务过多；异步失败是 HTTP 200 加 `status: failed`。仓库 [cn-adapter.ts](../src/lib/seedance/cn-adapter.ts) 的旧注释记的是「余额 < ¥5 时所有请求返回 403」，和文档不一致；无论哪种，都要保持上游余额充足。

对渠道类型的影响：

- Task Plugin（65）+ 内置 doubao 插件：首选，返回格式已实测对上（见 2.7）。插件提交和轮询走的正是上面的原生路径；插件没有默认地址，渠道地址要手填，只填域名 `https://token.xinhankr.com`。对客只开插件的原生路由，由 Portal 的 `/api/v3` 转发（见 2.7、2.8）。
- Openai Video（60）：排除，读不到 `data[0].url`（见 2.4）。
- NewAPI Video（59）：能读到这个地址，但只收三种比例、三档时长，和 2.5 的 `adaptive` 要求冲突，最多临时撑文生和参考生，同样要实测。
- OpenAI（1）：走 `/v1/videos`（见 2.5），文档里没有这条路径；仓库 [kling/proxy.ts](../src/lib/kling/proxy.ts) 记录 2026-08-10 用可灵模型实测这家时，这条路径返回 404。

这两篇是框架预置文档，同一框架的其他上游很可能有同样的原生接口。接入前先照上面的方法读对方文档，确认后可以照搬 Task Plugin 方案。

### 2.7 实测原生接口（2026-10-28）

用上游的平台 Key 直接打原生接口，不经过 new-api，一条 720p、4 秒、无参考视频的文生任务。目的是确认返回格式对不对得上内置 doubao 插件的解析。

模型名：这把 Key 的 `GET /v1/models` 只返回四个，`artsdance-2-5-pro-260801`、`artsdance-2-0-pro-260801`、`artsdance-2-0-fast-260801`、`artsdance-2-0-mini-260801`。文档推荐的 `doubao-seedance-2-5` 在这个账号上不存在。实测用 `artsdance-2-5-pro-260801` 提交，原生接口接受，且接受 `resolution: 720p`。

提交 `POST /api/v3/contents/generations/tasks`，1.6 秒返回：

```json
{ "id": "cgt-20261028162444-g8whm" }
```

轮询 `GET /api/v3/contents/generations/tasks/{id}`，210 秒后 `succeeded`，返回体（成片地址是火山 VOD 签名直链，约 24 小时过期，这里省略）：

```json
{
    "id": "cgt-20261028162444-g8whm",
    "model": "artsdance-2-5-pro-260801",
    "status": "succeeded",
    "content": { "video_url": "https://….vod.cn-north-1.volcvideo.com/…" },
    "usage": { "completion_tokens": 83485, "total_tokens": 83485 },
    "created_at": 1793204685,
    "updated_at": 1793204805,
    "seed": 71186,
    "resolution": "720p",
    "ratio": "16:9",
    "duration": 4,
    "framespersecond": 24,
    "service_tier": "default",
    "execution_expires_after": 3600,
    "generate_audio": true,
    "draft": false,
    "priority": 0,
    "output_format": "mp4"
}
```

插件关心的四项全部对上：任务号是 `cgt-` 形、状态 `succeeded`、成片在 `content.video_url`、`usage.completion_tokens` 非零。所以内置插件可用，不需要自定义插件。

成本：83,485 token，官方价 ¥70/百万即 ¥5.84，7 折进货 ¥4.09。折算每秒约 20,871 token，比 [cn-billing.ts](../src/lib/seedance/cn-billing.ts) 里 720p 的锚点 21,774 略低，可见每秒 token 不是严格线性。插件按真实 usage 结算，不受影响；只有 4.4 的按秒估算会有误差。

**对客入口要用插件的原生路由**。插件给客户开了两条提交路由，拼上游请求的方式不同（`plugins/tasks/doubao/plugin.js`）：

- `openai_video`（`POST /v1/videos`）：解码器原样收下请求体，但拼上游请求的 `buildSubmitRequest` 只取顶层的 `model`、`prompt`、`seconds` 和 `images`（只能是图片 URL 字符串），再加上 `metadata` 里的全部字段。顶层的 `videos`、`audios`、`resolution`、`ratio`、`duration`、`generate_audio` 会被静默丢掉：不报错，参数到不了上游，参考视频没发出去，分辨率和比例按上游默认出片。计费读的是 `metadata`，和实际发出的请求一致，完成时再按上游返回的 token 和分辨率结算，所以不会多收，问题是出片不是客户要的。客户只有把这些参数全部放进 `metadata`（参考素材放 `metadata.content`）才行。
- 原生路由（`POST /doubao/api/v3/contents/generations/tasks`）：`native.createTask` 把整个火山方舟请求体当成 `metadata`，拼上游请求时原样展开，`resolution`、`ratio`、`duration` 和参考素材都能到上游；计费的 `resolution`、`video_input` 也从同一份请求体读。

所以对客只开原生路由，客户按火山官方格式调用，见 2.8。`video_input` 只在提交时从 `content` 判断，完成时不更新；`extractUsageOnComplete` 用上游返回体的 token 和分辨率覆盖估值（实测返回体里有 `"resolution": "720p"`）。没传 `resolution` 时按 1080p 预扣，完成后按实际结算，余额紧的客户可能被预扣挡住。

### 2.8 Portal 的原生入口（2026-10-29）

`/api/v3/contents/generations/tasks`（提交）和 `/api/v3/contents/generations/tasks/{id}`（查询）由 [ark-native.ts](../src/lib/seedance/ark-native.ts) 转给 new-api 插件的原生路由。请求体和 Authorization 原样转发，鉴权、选渠道和计费都在 new-api。Portal 只做三处处理：

- 查询返回的是上游原始返回体，只替换了任务号，`model` 是上游名。Portal 按写死的 `UPSTREAM_TO_CLIENT_MODEL` 改回对客名。这张表必须与渠道的模型重定向逐条互逆，加模型时两处一起改；表里漏掉的 `artsdance` 名会原样返回并打告警日志。
- 提交带非空 `callback_url` 返回 400。插件会把它原样交给上游，上游回调会带上游任务号和上游模型名，与 #271（cn-adapter 的 `NEVER_FORWARD_KEYS`）是同一条规则。
- 查询缺 `status` 时补上。插件只在轮询拿到上游返回体后才更新任务数据：首次轮询前只有 `{id}`；轮询阶段判失败（上游 404、超时）时 `failTaskFromPoll` 只改任务状态，不改数据，不补的话客户永远等不到终态。Portal 用 new-api 通用任务查询 `GET /v1/video/generations/{id}` 读任务状态，补上 `queued`、`running` 或 `failed`，失败原因不透给客户。

与火山官方的差异写进了客户文档 `/docs#ark-native-video`：任务号是 new-api 的 `task_` 加 32 位字符，取消、删除、列表返回 404，不支持 `callback_url`。

API 子域的 Nginx 只放行这两条路径（[llmroute-api.conf](../deploy/nginx/llmroute-api.conf)），其余 `/api/*` 仍返回 404。Cloudflare 的 BIC、SBFM 例外规则原来只覆盖 `/v1/` 和 `/v1beta/`，表达式要补上这两条路径，见[部署与运维手册](../deploy/部署与运维手册.md) 6.3。

## 3. 渠道、分组与命名

- 客户调用的模型名必须写进渠道的模型列表，路由按字面匹配。发给上游的名字不同时，用模型重定向改。
- 新模型名不要以 `seedance2.0-`、`seedance2.5-` 开头。Portal 的 `/v1` 会把 [cn-adapter.ts](../src/lib/seedance/cn-adapter.ts) `MODEL_MAP` 里的名字（如 `seedance2.5-720p`、`seedance2.0-pro-1080p-ref`）转给 Portal 自带的 Seedance 适配器，不经过 new-api。这条链路只接受 Seedance 企业档的客户 Key，还要配置 `SEEDANCE_XHK_KEY`；生产没有配置这个变量，这类请求会失败。
- 一个渠道只放进一个分组。同时属于多个分组时，Portal 目录同步会提示「无法判断归属，本次不登记」。
- 在 new-api 新建分组并设好分组倍率。生产开了分组镜像（`NEWAPI_GROUP_SYNC_MODE=mirror`，见 [new-api 分组镜像](NEWAPI-GROUP-MIRROR-2026-10-13.md)），Portal 档次跟随 new-api 自动生成，不在 Portal 手动创建。客户能否选这个分组，跟随 new-api 的「用户可选分组」。

## 4. 定价

### 4.1 规则

- 计费方式选「按秒」或「按次」。按分辨率计价只填上游支持的分辨率，留空的分辨率会在发往上游前被拒。
- 除 Task Plugin 外不用「计费表达式」（见 2.1）；不要把上游按 token 的价格同步过来，59、60、1 都不按 token 结算。
- 定价货币保持美元。生产 Portal `USD_TO_CNY_RATE=1`，new-api QuotaPerUnit 为默认的 500000，编辑器里的 $1 就是客户付的 ¥1；new-api 没设站点展示币种，编辑器也只有美元可选。

### 4.2 扣费公式

客户实付（元）= 填的价 × 秒数（按次不乘）× 分组倍率，有限时折扣再乘折扣；quota = 实付 × 500000。失败任务扣 0。

2026-10-28 用生产现有任务核对：

| 模型                      | 计费      | 填的价 | 分组倍率 | 秒数 | 实扣 quota |   实扣 |
| ------------------------- | --------- | -----: | -------: | ---: | ---------: | -----: |
| video-v3                  | 按秒 720p |    7.5 |     0.12 |    5 |  2,250,000 |  ¥4.50 |
| video-v3                  | 按秒 720p |    7.5 |     0.12 |   15 |  6,750,000 | ¥13.50 |
| MiniMax-H3                | 按秒 768p |      1 |     0.12 |    5 |    300,000 |  ¥0.60 |
| video-v2-特价版           | 按次 720p |     25 |     0.12 |    5 |  1,500,000 |  ¥3.00 |
| video-v3-720P（按条计费） | 按次 720p |    170 |     0.12 |    5 | 10,200,000 | ¥20.40 |

### 4.3 每个分组先定口径

「填的价」和「分组倍率」的含义要按分组固定下来，否则很容易算错一个数量级。现有两种口径：

- 口径 A：填官方价，分组倍率 = 售价 ÷ 官方价（1 即按官方原价卖）。手册 2026-09-23「官方全局基础价与档次倍率分离」记录的「官方模型基础价固定按 GroupRatio=1 定义」即这种口径。
- 口径 B：填上游账户计价单位下的价，分组倍率 = 售价倍率 ÷ 充值兑换比例。[GPT-5.5 企业档定价](PRICING-TIERED-2026-09-17.md) 的 0.16（1.6 ÷ 10）属于这种。

两种口径下客户实付都按 4.2 计算。新建分组时在下表登记；现有两组的口径还没有记录，改价前先补上。

| 分组     | 分组倍率 | 口径   | 渠道 |
| -------- | -------: | ------ | ---- |
| 视频模型 |     0.12 | 待补记 | 8、9 |
| SD官转   |      7.5 | 待补记 | 12   |

### 4.4 把按 token 的上游价换成每秒价

每秒价 = 每秒 token 数 × 每百万 token 单价 ÷ 1,000,000。Seedance 的每秒 token 数约为 宽 × 高 × 24 ÷ 1024，仓库实测值见 [cn-billing.ts](../src/lib/seedance/cn-billing.ts) 的 `TOK_PER_SEC`。这组数是 2.0 实测的，2.5 沿用同一像素公式，上线后用真实 usage 校准。

以 Seedance 2.5 官方价（无参考视频）为例：

| 分辨率 | 每秒 token | 官方价 ¥/秒 | 7 折成本 ¥/秒 |
| ------ | ---------: | ----------: | ------------: |
| 480p   |     10,128 |       0.709 |         0.496 |
| 720p   |     21,774 |       1.524 |         1.067 |
| 1080p  |     48,992 |       3.772 |         2.641 |

填的价 = 目标售价 ÷ 分组倍率。

### 4.5 参考视频的成本缺口

上游按 token 计费时，参考视频的时长也计入 token；按秒计费只按输出秒数收。参考时长 ÷ 输出时长 > 售价相对官方价的倍数 ÷（进货折扣 × 含参考视频单价 ÷ 无参考视频单价）− 1 时开始亏本。例如 Seedance 2.5 720p 按官方价卖、7 折进货（含参考视频 42、无参考视频 70），阈值为 1 ÷（0.7 × 0.6）− 1 ≈ 1.38。参考视频用得多的渠道，要在分组倍率里留余量，或改用上报真实 token 的插件。

## 5. 上架与验收

1. 在 new-api 保存价格后，按秒、按次计费的模型要到 Portal 后台「模型」或「分组」页点「从 new-api 更新目录」，核对预览后点「确认同步」，不做这一步客户在目录和价格页看不到新模型。任务表达式（`u(...)`）计费的模型会被这一步跳过（提示「计费规则无法同步」），不用同步，见 6.2。
2. 用新分组建测试 Key，充少量余额，跑一条最便宜的真实任务（如 mini、480p、4 秒）并轮询到结束，逐项核对：
    - 拿到可播放的成片地址；
    - new-api 日志里的扣费符合 4.2，并与上游后台的实际扣费对得上；
    - 不支持的分辨率在本地返回 400；
    - 失败的任务扣 0。
3. 上游支持参考视频时，再跑一条带参考视频的任务，看实际成本差多少。
4. 用第 7 节的查询读回任务的计费快照（计费方式、分辨率、单价、分组倍率）。

### 6.2 这次踩到的坑

- 新建渠道表单的分组默认带 `default`。`default` 没有分组倍率，new-api 按 1 倍计费，等于按官方价的 1/7.5 卖，必须删掉只留目标分组。
- 删除渠道会连 Key 一起删。只换渠道类型时用编辑抽屉的「更换提供商」，渠道编号不变。
- 选插件会把插件声明的模型全部填进模型列表（doubao 是 8 个），要删到只剩卖的几个；不要点「获取模型」，会把上游名拉回来。
- 渠道保存后，「模型定价 → 未设置价格模型」才会出现「分辨率 × 参考视频」矩阵。每个模型单独点「保存模型价格」，看到「模型定价已保存」才算存上。
- 生产 Portal 是分组镜像模式，后台没有「替换渠道」，档次登记跟随 new-api，打开渠道分组页即对账。「从 new-api 更新目录」会跳过 `u(...)` 表达式的模型，价格页暂时看不到这四个模型，不影响 `/api/v3` 调用。
- new-api `/api/pricing` 对没定价的模型显示 `model_ratio: 37.5`，只是默认显示值；没定价的模型仍在发往上游前被拒。任务计费快照里的 `billing_mode` 可能显示 `per-second`，实际按表达式扣费（6.3 的扣费与表达式结果一致）。

## 7. 只读核对方法

复用本机已有的 `llmroute-prod` SSH 主连接（先 `ssh -O check llmroute-prod`；没有主连接时按手册 0.9 节先建立），强制只读并限时 20 秒：

```bash
ssh -o ClearAllForwardings=yes -o BatchMode=yes llmroute-prod 'docker exec -i -e PGOPTIONS="-c default_transaction_read_only=on -c statement_timeout=20000 -c TimeZone=Asia/Shanghai" postgres psql -X -q -U root -d new-api' < check.sql
```

脚本第一行先执行 `SELECT current_setting('transaction_read_only');`，结果须为 `on`。查 Portal 库时把容器换成 `silkroadai-portal-db`，参数换成 `-U portal -d silkroadai_portal_prod`。不要查询 `channels.key`、`tasks.private_data` 全文，以及代理、请求头覆盖、参数覆盖的具体值。

某个模型在各价格配置里的条目：

```sql
SELECT o."key", e.key AS model, e.value
FROM options o
CROSS JOIN LATERAL jsonb_each(CASE WHEN coalesce(o.value, '') ~ '^\s*\{' THEN o.value::jsonb ELSE '{}'::jsonb END) e
WHERE o."key" IN ('ModelPrice', 'ModelRatio', 'billing_setting.billing_mode', 'billing_setting.billing_expr',
                  'billing_setting.task_billing_pricing', 'billing_setting.scheduled_discount')
  AND e.key = 'artsdance-2-5-pro-260801';
```

任务的计费快照：

```sql
SELECT t.id, t.status, t.quota,
       t.properties::jsonb ->> 'video_seconds' AS seconds,
       t.private_data::jsonb -> 'billing_context' ->> 'billing_mode'       AS mode,
       t.private_data::jsonb -> 'billing_context' ->> 'billing_resolution' AS res,
       t.private_data::jsonb -> 'billing_context' ->> 'model_price'        AS price,
       t.private_data::jsonb -> 'billing_context' ->> 'group_ratio'        AS group_ratio
FROM tasks t
WHERE t.properties::jsonb ->> 'origin_model_name' = 'video-v3'
ORDER BY t.id DESC LIMIT 20;
```
